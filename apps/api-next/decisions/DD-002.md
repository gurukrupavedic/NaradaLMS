# DD-002: Keep the draft's exam transition/concurrency hardening

**Status:** proposed

## 1. Current behavior

`apps/api/src`'s exam update/result endpoints are the compatibility baseline: whatever
transitions and concurrency guarantees they currently provide (see `src/services/exam.ts`,
`src/routes/exams.ts`). The draft (`apps/api-next/src/exams/transitions.ts`, covered by
`transitions.test.ts`) independently implements a state machine (`scheduled -> inProgress`,
`scheduled -> cancelled`, `inProgress -> cancelled`, no exit from terminal states), an
optimistic `WHERE id = ? AND status = previouslyReadStatus` guard, and a transactional
single-result-winner for `POST /exams/:examId/results` (insert evaluation, update exam to
completed guarded by `evaluationId IS NULL`, roll back the evaluation insert if the guard
loses).

That result guard is incomplete. Recordability is checked before the transaction, but the
transactional update does not compare the exam status. A concurrent cancellation can commit
after the read and before the result update; the result transaction can then overwrite the
terminal `cancelled` state with `completed`. The current code is safe against two result writers,
but not against a result writer racing a status transition.

## 2. Problem/opportunity

This is exactly the kind of "internal pattern" §1.3 allows without approval **if** it
preserves every externally observable compatibility-baseline item — but PARITY_PLAN.md
§11.5–§11.6 treats it as a candidate improvement because it isn't yet verified that the
old backend's observable transition/concurrency behavior is identical (e.g. whether a
losing concurrent transition currently returns 409 vs some other status, and whether a
double result-record attempt in `src/services/exam.ts` is race-safe at all today).

## 3. Proposed behavior

Retain the draft's state machine and optimistic update guard. Strengthen transactional result
recording so the completion update compares all of:

- exam ID;
- the exact recordable status read before the transaction; and
- `evaluationId IS NULL`.

If the guarded update loses, throw inside the transaction so the inserted evaluation rolls back.
Keep the approved 404/409 distinction after comparing against the current row. This proposal is
still conditional on the compatibility decision for transition and concurrency behavior.

## 4. Alternatives

- **Baseline:** reimplement whatever `apps/api/src/services/exam.ts` currently does,
  including any gaps (e.g. if it does not race-guard result recording today).
- **Existing draft guard:** keep the state machine and `evaluationId IS NULL` result guard, while
  accepting that cancellation can be overwritten.
- **Proposed:** keep the state machine and add exact-status compare-and-set to result recording.
- **Hybrid:** keep the draft's concurrency guards (no orphan evaluations, no double
  completion) but relax the transition table if the old backend permits transitions the
  draft currently disallows.

## 5. Impact analysis

Affects `PATCH /exams/:examId` and `POST /exams/:examId/results` only. No migration.
Primary risk is silently tightening validation beyond what current API consumers (the
web app) rely on — e.g. if the web app depends on a transition the draft's machine
forbids.

## 6. Compatibility/rollout plan

Land alongside the exam ACL work in Phase 5 once DD-003/DD-004/DD-005 are also resolved,
since all four touch the same module. No flag needed; this is server-side only.

## 7. Acceptance criteria

Full transition table test (already present), plus integration coverage for:

- invalid/concurrent transition;
- terminal result rejection;
- two simultaneous result attempts with exactly one evaluation committed;
- cancellation winning against result recording, leaving zero evaluations;
- result recording winning against cancellation, leaving one completed exam and one evaluation;
- no orphan evaluation after any losing result transaction.

The wider exam acceptance matrix remains in `PARITY_PLAN.md` §11.7.
