# DD-013: HTTP datetime and meeting-URL policy

**Status:** approved (agent decision, pending human review — see §8)

## 1. Current behavior

Verified directly against the real schema files:

- `apps/api-next/src/exams/schema.ts::ExamSchema` — `scheduledAt: z.coerce.date()`,
  `performedAt: z.coerce.date().nullable()`.
- `apps/api-next/src/batches/schema.ts::BatchSchema` — `startDate: z.coerce.date().nullable()`,
  `meetingUrl: z.url().nullable()`.
- `CreateExamSchema`/`UpdateExamSchema` and `CreateBatchSchema`/`UpdateBatchSchema` are all
  `.pick()`/`.partial()` derivations of these same two base objects — so today's input
  validation for `scheduledAt` and `startDate` is exactly `z.coerce.date()`, and for
  `meetingUrl` exactly `z.url()`.

`z.coerce.date()` calls `new Date(input)` and rejects only `NaN` results — it therefore
**accepts** raw epoch-millisecond numbers, offset-free ISO strings (`"2024-01-01T00:00:00"`,
interpreted in the server's local timezone), and date-only strings (`"2024-01-01"`), all of
which HARDENING_PLAN §10.2 requires rejecting. It does correctly reject `null`, booleans, and
impossible calendar dates (`new Date("2024-13-40")` is `Invalid Date`).

`z.url()` validates only that the value parses as *some* URL via the `URL` constructor — it
accepts `http:`, `javascript:`, `data:`, `mailto:`, `ftp:`, and userinfo-bearing URLs
(`https://user:pass@host/...`) equally. Verified directly (`node -e ...` against the installed
`zod@4.4.3`): all of those currently pass `BatchSchema.shape.meetingUrl`'s validation.

**Where this is actually exercised at runtime — checked, not assumed:** `ExamSchema` and
`BatchSchema` (the objects with these coercions) are **never** `.parse()`d against an outgoing
response row — `exams/route.ts`/`batches/route.ts` write `res.json({ data: exam })` directly from
the repository's row, with no schema re-validation on the way out. The only place these
coercions run at runtime is the `.pick()`-derived create/update input schemas. This matters for
scoping (§3).

## 2. Problem/opportunity

Both gaps are real, immediately exploitable-shaped input-validation holes on the two currently
implemented write paths (`POST/PATCH /batches`, `POST/PATCH /exams`):

- A client can submit `scheduledAt` as a raw number, a date-only string, or an offset-free
  string, and the server will silently accept and store a `Date` interpreted under an ambiguous
  or server-local timezone rule instead of the exact client-intended instant.
- A client can submit `meetingUrl` as `javascript:...`, `data:...`, or a credential-bearing URL,
  and it will be stored and later rendered as a "join meeting" link — a real stored-XSS/
  credential-leak shape if the web client ever treats it as clickable without its own
  revalidation (HARDENING_PLAN §10.3's last acceptance bullet — "confirm the web client treats
  the value as an external link and does not reinterpret it" — is a client-side check out of
  this note's scope, but tightening the server-side input is the defense that doesn't depend on
  the client getting that right).

## 3. Proposed behavior

**Datetime**: replace `z.coerce.date()` with Zod v4's built-in `z.iso.datetime({ offset: true })`
(verified directly against the installed version — accepts a `Z`-suffixed or explicitly-offset
ISO-8601 string, rejects offset-free/date-only strings, rejects non-string input including
numbers, rejects impossible calendar dates), then `.transform(value => new Date(value))` to get
a `Date` for the same downstream shape as today. New shared helper in
`apps/api-next/src/utils/validate.ts`:

```ts
/** ISO-8601 instant with `Z` or an explicit offset (HARDENING_PLAN.md H6/DD-013) — rejects
 * offset-free timestamps, numbers, and non-instant strings; not accepted by `z.coerce.date()`. */
export const isoInstant = z.iso.datetime({ offset: true }).transform(value => new Date(value))
```

Apply to `exams/schema.ts::ExamSchema.scheduledAt`/`performedAt` and
`batches/schema.ts::BatchSchema.startDate` (keep the existing `.nullable()` wrapper where
present — this proposal doesn't touch null-acceptance, see §3's scoping note below).

**Meeting URL**: HTTPS-only, no userinfo. New shared helper, same file:

```ts
/** HTTPS-only URL with no embedded credentials (HARDENING_PLAN.md H6/DD-013). */
export const httpsUrl = z.url({ protocol: /^https$/ }).refine(value => {
  try {
    const url = new URL(value)
    return url.username === '' && url.password === ''
  } catch {
    return false
  }
}, 'meeting URL must not contain credentials')
```

**Correction (caught during planning, not in the original draft of this note):** the refine
above must wrap `new URL(value)` in `try/catch`. Without it, Zod still runs the refine even
after the `protocol` regex has already rejected the value, and `new URL('//host/path')` — one of
this note's own required-reject inputs (protocol-relative URLs) — *throws* a `TypeError` rather
than returning a parse failure. That exception propagates out of `safeParse`/`safeParseAsync`
uncaught, which `utils/validate.ts::parse` would surface as an unhandled 500, not the intended
400. The `try/catch` is required for `httpsUrl` to actually behave as specified, not an
optional hardening.

Apply to `batches/schema.ts::BatchSchema.meetingUrl` (keep `.nullable()`).

**No approved localhost/non-HTTPS exception.** HARDENING_PLAN §10.3 allows one "if local
development needs non-HTTPS links" via "explicit test fixtures or a narrowly approved localhost
exception" — I'm not adding a code-level exception; if local dev needs to exercise a non-HTTPS
meeting URL, that's a test-fixture concern (mock the value in tests), not a schema carve-out
that would also work in production.

**Scoping note — HARDENING_PLAN §10.1 (full 7-way schema separation) is explicitly OUT of
scope for this note.** §10.1 asks for independent schemas for create body / update body / route
params / list query / decoded cursor / database row / response projection, and warns against
building write schemas by `pick`/`partial` from a schema "containing persistence-oriented
coercions or response nullability" — which is literally what `CreateExamSchema`/
`CreateBatchSchema` do today (`.pick()` from `ExamSchema`/`BatchSchema`). I checked whether this
is an active runtime bug (§1) and confirmed it is **not**: the base schemas are never parsed
against a response row, so there's no double-duty coercion happening on output today. Doing the
full 7-way split now would touch both domains' entire schema surface for a structural/
maintainability concern with no currently-observable behavior bug, which is a larger, riskier
change than this note's two concrete, high-confidence fixes. I'm deferring it — recorded here so
it isn't silently dropped, not fixed as part of DD-013.

## 4. Alternatives

- **Baseline (no change):** keep `z.coerce.date()`/`z.url()`. Rejected — both are real,
  already-identified gaps matching HARDENING_PLAN §10.2/§10.3's exact required-reject lists.
- **Hand-rolled regex datetime validation instead of `z.iso.datetime`:** more code, more surface
  for a subtly-wrong regex, no benefit over the built-in Zod v4 primitive, which I verified
  behaves exactly as required. Rejected in favor of the built-in.
- **`z.url()` with a custom refine instead of the `protocol` option:** the `protocol` regex
  option is built into Zod v4's `z.url()` and verified to reject every scheme HARDENING_PLAN
  §10.3 lists (http, javascript, data, mailto, ftp, protocol-relative). Only the
  credential-bearing case needs an additional `.refine`. Using the built-in option for the
  scheme check and a minimal refine only for the one gap it doesn't cover is simpler than a
  fully hand-rolled URL validator.
- **Full §10.1 schema separation now:** rejected for this note per §3's scoping reasoning; a
  larger, separate, structural change with no currently-observable bug behind it.

## 5. Impact analysis

- Affects `POST /batches`, `PATCH /batches/:batchId` (`startDate`, `meetingUrl`) and
  `POST /exams`, `PATCH /exams/:examId` (`scheduledAt`). No route/response-shape change — only
  input acceptance narrows.
- **Real client-visible narrowing**: any existing caller sending an offset-free datetime, a raw
  timestamp number, or a non-HTTPS/credentialed meeting URL will now get a 400 instead of a
  silently-accepted write. This is the explicit intent of H6, not a side effect — worth a web-
  client check before rollout (same caveat pattern as DD-001's row 5 and DD-002).
- No schema/migration impact — the stored column types (`timestamp`, `text`) are unchanged;
  only the HTTP input contract narrows.

## 6. Compatibility/rollout plan

No feature flag. Recommend confirming `apps/web`'s batch-schedule and exam-scheduling forms
always send `Z`-or-offset ISO strings (most JS `Date#toISOString()` calls already produce `Z`
suffixed strings, so this is likely already compatible) and HTTPS meeting URLs before/alongside
rollout — flagged, not verified here (no `apps/web` changes are part of this note).

## 7. Acceptance criteria

Matching HARDENING_PLAN §10.2/§10.3's required-test lists exactly, as unit tests against the new
`isoInstant`/`httpsUrl` schemas directly (in `apps/api-next/src/utils/validate.test.ts`, new
file) plus the domain schemas that use them:

- `isoInstant` rejects: `null`, numbers, booleans, empty string, `"2024-13-40T00:00:00Z"`
  (impossible calendar date), `"2024-01-01T00:00:00"` (offset-free), `"2024-01-01"` (date-only).
- `isoInstant` accepts: `"2024-01-01T00:00:00Z"`, `"2024-01-01T00:00:00+05:30"`,
  `"2024-01-01T00:00:00-08:00"`, and round-trips each to the same instant
  (`new Date(input).toISOString()` matches the parsed `Date`'s `.toISOString()`).
- `httpsUrl` rejects: `"javascript:alert(1)"`, `"data:text/html,x"`, `"mailto:a@b.com"`,
  `"ftp://host/x"`, `"//host/path"` (protocol-relative), `"http://host"`,
  `"https://user:pass@host"` (credential-bearing).
- `httpsUrl` accepts: `"https://zoom.us/j/123"` and similar ordinary HTTPS links.
- `CreateExamSchema`/`UpdateExamSchema` reject the same bad `scheduledAt` inputs end-to-end;
  `CreateBatchSchema`/`UpdateBatchSchema` reject the same bad `startDate`/`meetingUrl` inputs
  end-to-end.
- The web-client link-reinterpretation acceptance bullet (HARDENING_PLAN §10.3's last item) is
  explicitly out of scope for this note (server-only).
