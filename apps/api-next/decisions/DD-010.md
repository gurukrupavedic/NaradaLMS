# DD-010: Fail closed on unknown school roles rather than normalizing to `member`

**Status:** proposed

## 1. Current behavior

Verified directly in code: `apps/api-next/src/utils/accessPolicy.ts`'s
`normalizeSchoolRole` currently does:

```ts
function normalizeSchoolRole(role: typeof member.$inferSelect.role | undefined): SchoolRole {
  if (role === 'owner' || role === 'admin') {
    return role
  }
  return 'member'
}
```

Any role value that isn't exactly `'owner'` or `'admin'` — including an unrecognized/
future/corrupted role string — is silently normalized down to `'member'` rather than
rejected. It is not yet confirmed whether `apps/api/src`'s BetterAuth role handling does
the same normalization or fails closed on an unknown role today.

## 2. Problem/opportunity

Silently downgrading an unknown role to `member` is a fail-open pattern: if a new role
value is ever introduced upstream (BetterAuth config change, data migration, manual DB
edit) before the draft's `SchoolRole` union is updated to recognize it, the holder of
that unknown role quietly gets `member`-level access instead of being denied — the wrong
direction for a permission fallback. PARITY_PLAN.md §4.4 explicitly calls for "unknown
role strings deny access."

## 3. Proposed behavior

`normalizeSchoolRole` (or its replacement once `AccessPolicy` is expanded per
PARITY*PLAN.md §6.4) throws/denies when `role` is present but not one of the recognized
values, rather than defaulting to `'member'`. A **missing** membership (no row at all)
continues to deny access except for super admins, per existing behavior — this DD is only
about a \_present-but-unrecognized* role value, not the missing-membership case.

## 4. Alternatives

- **Baseline:** keep normalizing unknown roles to `member` (current draft code, matches
  whatever `apps/api/src` does if it also normalizes — needs verification).
- **Proposed:** fail-closed on unknown roles (current draft's own stated design intent
  per PARITY_PLAN.md §4.4, but not yet what the code actually does).

## 5. Impact analysis

Only matters if an unrecognized role value can actually occur — check `@narada/auth`'s
role enum/schema to see whether the DB column is constrained to `owner | admin | member`
already (in which case this is theoretical) or whether it's a free-form string/wider
enum that could admit future values the draft doesn't know about yet.

## 6. Compatibility/rollout plan

No migration. Pure code change in `AccessPolicy`. Should land as part of Phase 1's
AccessPolicy expansion (PARITY_PLAN.md §6.4), not standalone, since that's where the
typed permission checks are being built out anyway.

## 7. Acceptance criteria

Test: a membership row with a role value outside `owner | admin | member` (constructed
directly in test fixtures even if the production schema can't currently produce one)
results in `forbidden()`, not silent `member` treatment.
