# DD-001: Use `translateDbError` as a final race-safe mapping for unique/FK failures

**Status:** proposed

## 1. Current behavior

`apps/api/src` has no centralized database-error translation layer (no `dbError.ts`
equivalent; grep for `unique_violation`/`23505`/`23503`/`PostgresError` in `apps/api/src`
returns nothing). Endpoints instead do a check-then-write precheck — e.g.
`src/routes/batches.ts` calls `findBatchById` before update/delete to decide 404 vs proceed,
but does not catch a unique/foreign-key violation that a concurrent request could still
trigger between the check and the write. In that race, the current backend most likely
surfaces an unhandled 500 rather than a domain 409/422.

## 2. Problem/opportunity

Check-then-write has a TOCTOU gap under concurrent requests (e.g. two clients creating a
batch with the same `code` at once, or inserting an evaluation referencing a
just-deleted chapter). `apps/api-next/src/utils/dbError.ts` already exists and is unit
tested (`dbError.test.ts`); using database constraints as the final race-safe guard would make
these failures return a controlled domain response instead of leaking a raw 500.

The current translator is too coarse to be the complete solution: SQLSTATE `23503` can mean
either that an inserted parent does not exist or that a delete/update is blocked by an existing
child. Mapping both cases to `referenced resource does not exist` is incorrect. For example, an
evaluator-profile delete blocked by `evaluation.evaluatorId` is a resource-in-use conflict, not
a missing reference.

## 3. Proposed behavior

Use two translation layers:

1. A domain service maps known constraint names plus operation context to the same specific
   `AppError` the friendly precheck path would have produced.
2. `translateDbError` remains a final safety net for recognized integrity failures, but returns
   only a truthful generic response when domain meaning is unavailable. It must not claim that a
   referenced resource is missing merely because the SQLSTATE is `23503`.

This retains database constraints as the race-safe authority while allowing create-side missing
references, delete-side resource-in-use conflicts, and unique violations to have different
semantics.

## 4. Alternatives

- **Baseline (no change):** keep relying solely on check-then-write; concurrent races
  produce a 500. Simpler, but reintroduces a known race class the draft already has
  tooling to close.
- **SQLSTATE-only translation:** keep the current draft's global 409-for-unique and 422-for-FK
  mapping. Simple, but produces false messages and sometimes the wrong status for delete-side
  violations.
- **Proposed:** constraint/operation-aware domain translation plus a conservative global safety
  net.
- **Precheck + row-level lock:** use `SELECT ... FOR UPDATE` or a serializable
  transaction instead of relying on constraint-violation translation. More invasive,
  changes transaction shape for every affected write, not clearly justified here.

## 5. Impact analysis

- Affects any endpoint with a unique or FK constraint reachable via a mutation: batch `code`,
  school `slug`, enrollment composite key, exam/evaluation FKs, and profile deletion.
- No schema/migration impact — purely error-handling.
- No client contract change on the success path; only changes the response for an
  already-rare race condition (previously undefined/500, now a defined 409/422).
- Observability: fewer unhandled 500s in logs for this specific race; should reduce
  noise, not increase it.

## 6. Compatibility/rollout plan

No rollout coordination needed — this only changes behavior on a race window that
currently has no defined contract. No feature flag needed. No rollback concern beyond
reverting the middleware wiring.

## 7. Acceptance criteria

- A test that fires two concurrent creates with the same unique key and asserts exactly
  one 2xx and one clean 409 (no 500, no unhandled rejection).
- A test that inserts a row referencing a concurrently deleted parent and asserts the approved
  missing-reference response, not 500.
- A delete blocked by a child row returns the approved resource-in-use response and never says
  that the child/parent does not exist.
- `dbError.test.ts` and integration coverage include the specific constraint names in play for
  each domain once identified (batch code, school slug, enrollment composite key, profile
  assessment references).
- An unknown integrity constraint returns a safe response without exposing its constraint name.
