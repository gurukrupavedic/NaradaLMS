# DD-014: Deterministic request-context failure precedence

**Status:** approved (agent decision, pending human review — see §8)

## 1. Current behavior

`apps/api-next/src/naradaRoute.ts` resolves request context as follows, verified directly:

- `publicRoute`: no school/session resolution at all. Correct, no bug (HARDENING_PLAN §9.1:
  "Public routes must not resolve a school").
- `schoolRoute`: calls `resolveSchool(req)` alone. `resolveSchool` checks the `X-School-Slug`
  header is present (400, no I/O, before any query) — correct — then queries
  `publicDb.query.organization.findFirst(...)` for the slug. **If no school matches, it throws
  `badRequest('school not found')` — a 400.** PARITY_PLAN.md line 274 already documents this as
  a known compatibility gap: "Unknown school slug: 404, not the draft's current 400." This has
  not yet been fixed.
- `userRoute` and `profileRoute` both do:
  ```ts
  const [{ db, school }, user] = await Promise.all([
    resolveSchool(req),
    SessionService.getCurrentUser(req),
  ])
  ```
  `resolveSchool` (school header format check, then a DB query for the org) and
  `SessionService.getCurrentUser` (session header/cookie check, then a BetterAuth session
  lookup) run **concurrently**, not in the sequence HARDENING_PLAN §9.1 recommends (header
  format → session → school lookup). Two consequences, both real:
  1. **Wasted I/O**: the school DB query fires even when the session is invalid/missing and the
     request will end in 401 regardless.
  2. **Non-deterministic precedence**: `Promise.all` rejects with whichever input promise
     rejects first in real wall-clock time. If a request has both an invalid session and an
     unknown school slug, whether it gets 401 or 404 depends on which async operation happens
     to settle first — not on any documented priority. This is exactly the failure mode
     HARDENING_PLAN §9.2's first acceptance criterion exists to rule out: "every pair of
     simultaneous invalid conditions has one stable documented response."
- `profileRoute` additionally calls `resolveProfile(req, db, user)` (400 missing header / 403
  foreign-or-missing profile) and then `AccessPolicy.load({ db, school, user, profile })`, whose
  first step queries `publicDb.query.member` and throws `forbidden()` (403) if the actor has no
  organization membership and isn't a super admin. **The membership check therefore runs AFTER
  profile resolution**, whereas HARDENING_PLAN §9.1's recommended order places "missing
  organization membership: 403" (item 4) before "missing/invalid required profile header:
  approved 400/403 behavior" (item 5). A request with both a foreign profile header and no
  membership currently gets `resolveProfile`'s 403 (or 400 for a missing header) rather than the
  membership 403 the recommended order would produce first.
- `SessionService` (`session.ts`) already caches the session promise per request in a
  `WeakMap<Request, Promise<AuthenticatedSession>>` — §9.2's "session ... resolve at most once
  per request" is already satisfied. `resolveSchool`/`resolveProfile` have no explicit cache, but
  since each wrapper calls each of them at most once today, there's no actual duplicate-resolution
  bug — just no explicit guarantee if a future change called either twice.

## 2. Problem/opportunity

Two concrete, already-observable bugs, not hypothetical ones:

1. The 400-instead-of-404 for an unknown school slug is a **documented compatibility gap**
   (PARITY_PLAN.md line 274) that has simply not been implemented yet.
2. The `Promise.all` race means the API's behavior for two simultaneously invalid conditions
   (e.g. bad session + unknown school) is **not deterministic** — it depends on relative timing
   of a BetterAuth session lookup vs. a Postgres query, neither of which has a documented or
   guaranteed ordering. This directly violates HARDENING_PLAN §9.2's first acceptance bullet.

Both are fixable without any route/schema/response-shape change — this is entirely about
*which* error a given combination of bad inputs produces, and *when* I/O happens, not about
adding new checks.

## 3. Proposed behavior

**Fix 1 — `resolveSchool`: unknown slug → 404.** Change `throw badRequest('school not found')`
to `throw notFound('school not found')` (import `notFound` from `./error`, already used
elsewhere in this file's sibling modules). No other change to `resolveSchool`.

**Fix 2 — sequential resolution in `userRoute`/`profileRoute`, with the header check split out.**

```ts
function requireSchoolSlug(req: Request): string {
  const slug = req.get('x-school-slug')
  if (!slug) {
    throw badRequest('X-School-Slug header is required')
  }
  return slug
}

export function userRoute(handler: (args: UserRouteArgs) => Promise<void>): RequestHandler {
  return async (req, res) => {
    requireSchoolSlug(req)
    const user = await SessionService.getCurrentUser(req)
    const { db, school } = await resolveSchool(req)
    await handler({ req, res, db, school, user })
  }
}
```

(and identically for `profileRoute`, before its existing `resolveProfile`/`AccessPolicy.load`
calls). `resolveSchool` itself calls `requireSchoolSlug` first (synchronously, before opening
the cached promise — see fix 3), so `schoolRoute` keeps its exact current behavior. This makes
the true order: missing header → 400 (no I/O) → invalid session → 401 → unknown slug → 404,
deterministically — the school query never fires for a request that was always going to 400 or
401 regardless.

**Correction (caught during planning, not in the original draft of this note):** the paragraph
above originally claimed the malformed-header case would short-circuit before the session
lookup "without needing to split `resolveSchool` into two functions." That claim was wrong: once
`SessionService.getCurrentUser(req)` is awaited *before* `resolveSchool(req)` (as fix 2 requires,
to get session-before-school-lookup ordering), the header check — which lives inside
`resolveSchool` — no longer runs first. A malformed-header request would incorrectly trigger a
real session lookup before its 400 surfaces, regressing HARDENING_PLAN §9.1 item 1 ("400 without
I/O") relative to today's code (where `resolveSchool`'s synchronous throw currently wins the
`Promise.all` race deterministically).

The actual fix: split the header-presence check out of `resolveSchool` into a tiny synchronous
helper, `requireSchoolSlug(req): string`, called before `SessionService.getCurrentUser` in both
`userRoute` and `profileRoute`. `resolveSchool` itself calls `requireSchoolSlug` too (so
`schoolRoute`, which doesn't involve a session, is unaffected). This makes the true order
1 (header, no I/O) → 2 (session) → 3 (school lookup), matching §9.1 exactly, with the missing-header
case never triggering a session lookup or school query.

**Fix 3 — explicit per-request school cache**, mirroring `SessionService`'s existing pattern,
for defense-in-depth conformance to "school ... resolve at most once per request" (currently
true structurally but not guaranteed against a future change that calls `resolveSchool` twice):

```ts
const schoolCache = new WeakMap<Request, Promise<{ db: SchoolDbClient; school: School }>>()

function resolveSchool(req: Request): Promise<{ db: SchoolDbClient; school: School }> {
  const cached = schoolCache.get(req)
  if (cached) return cached

  const slug = requireSchoolSlug(req) // synchronous, before the promise is created or cached
  const promise = (async () => {
    const school = await publicDb.query.organization.findFirst({
      where: (t, { eq }) => eq(t.slug, slug),
    })
    if (!school) throw notFound('school not found')
    return { db: getSchoolDb(school.id), school }
  })()

  schoolCache.set(req, promise)
  return promise
}
```

(`resolveSchool` is deliberately not declared `async`, so the missing-header throw stays
synchronous rather than becoming an implicitly-caught rejected promise.)

**Deferred, not fixed by this proposal — the membership-before-profile-header ordering.**
HARDENING_PLAN §9.1 places membership (item 4) before the profile header check (item 5); today
`profileRoute` does the reverse. Fixing this properly requires either (a) `AccessPolicy.load`
performing its membership check before `resolveProfile` runs (meaning `profileRoute` would need
to restructure to call a membership-only step, then `resolveProfile`, then finish loading batch
roles), or (b) duplicating the membership query. Both are more invasive than fixes 1–3 and touch
`AccessPolicy`, which DD-003–DD-005 (exam ACL work, not yet landed) will also restructure. I'm
choosing **not** to reorder this now: the risk of a subtly wrong refactor to `AccessPolicy.load`
under no test coverage of the exact precedence outweighs closing an ordering gap whose only
externally observable effect is which of two 403s (or a 400 vs 403) a request with *multiple*
simultaneously-wrong things gets — itself a fairly narrow edge case compared to fixes 1–2's session/school race and status-code bug. Recorded here explicitly so it isn't silently forgotten; worth revisiting once DD-003–DD-005 land and touch `AccessPolicy` anyway.

## 4. Alternatives

- **Baseline (no change):** keep `Promise.all` and the 400-for-unknown-slug behavior. Rejected:
  leaves a documented compatibility gap unfixed and a real non-determinism bug in place.
- **Full reorder including membership-before-profile:** closes every gap in §9.1's list in one
  change. Rejected for now per §3's reasoning — larger blast radius on `AccessPolicy`, better
  done alongside the exam-ACL work that will touch the same class.
- **Proposed:** fix the 404 status code and the school/session race (fixes 1–2, both low-risk,
  both already-identified concrete bugs), add the explicit school cache (fix 3, defense-in-depth,
  zero behavior change), defer the membership/profile-header reorder with reasoning recorded.

## 5. Impact analysis

- Affects every route using `schoolRoute`, `userRoute`, or `profileRoute` (i.e. every
  school-scoped endpoint currently implemented: profiles, batches, exams).
- **One real status-code change**: an unknown school slug now returns 404 instead of 400. This
  is the PARITY_PLAN-documented target behavior, not a novel deviation — approving this DD is
  what turns that already-recorded gap into implemented behavior. Any client currently branching
  on 400 for this case would need to switch to 404; PARITY_PLAN.md already treats 404 as the
  correct target, so this isn't expected to be a surprise to whoever owns the web client.
- No other status code changes. The session/school reordering only changes *which* of two
  already-defined errors surfaces when both conditions are true simultaneously — a case that
  currently has no stable behavior to preserve.
- No schema/migration impact.

## 6. Compatibility/rollout plan

No feature flag needed; server-side only, no client contract change beyond the one 404 fix
(which brings the draft in line with the already-documented compatibility target, not away from
it). No rollback concern beyond reverting `naradaRoute.ts`.

## 7. Acceptance criteria

- `resolveSchool` with an unknown slug throws a 404, not 400 (unit test on `resolveSchool`
  directly, or via `schoolRoute`/`userRoute`/`profileRoute` with a stubbed `publicDb`).
- A request with a missing/invalid session AND an unknown school slug deterministically gets
  401, never 404 — proven by a test where the school lookup is stubbed to resolve slower than
  session validation would in the old racy code (e.g. delay the mocked school query), confirming
  the new code never even calls it before the session check settles.
- A request with a malformed/missing `X-School-Slug` header never performs a session lookup or
  a school DB query (both should be observably uncalled) — the header-format check must still
  run before any `await`.
- The explicit school cache: two hypothetical calls to `resolveSchool` within one request
  resolve to the same cached promise (test by calling it twice with the same `req` object and
  asserting the underlying `publicDb.query.organization.findFirst` mock was invoked once).
- Existing behavior for every other case (valid school + valid session, valid school + invalid
  session, invalid school + valid session) unchanged in outcome, only reordered in timing.
