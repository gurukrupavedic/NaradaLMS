# DD-006: Evaluate school permissions from `X-School-Slug` + persisted membership instead of BetterAuth `activeOrganizationId`

**Status:** proposed

## 1. Current behavior

The current backend resolves school permissions via BetterAuth's `activeOrganizationId`
(the organization the session considers "active"), not by re-deriving membership from the
school resolved via the `X-School-Slug` request header.

## 2. Problem/opportunity

Multi-tab/multi-school usage can desync `activeOrganizationId` from the school the caller
is actually addressing via `X-School-Slug` — a user active in School A but issuing a
request scoped to School B via the header could be evaluated against the wrong
organization's permissions, or rejected/allowed incorrectly. Resolving permissions
directly from the header-selected school and a persisted-membership lookup (already how
`apps/api-next/src/utils/accessPolicy.ts` `AccessPolicy.load` works today) removes the
session-side-channel dependency.

## 3. Proposed behavior

Permissions are evaluated solely from: the school resolved by `X-School-Slug` + a
`member` row query for `(organizationId, userId)` — exactly the draft's current
`AccessPolicy.load` implementation. `activeOrganizationId` is not consulted.

## 4. Alternatives

- **Baseline:** replicate `activeOrganizationId`-based resolution, requiring the draft
  to also set/track active-organization state to match.
- **Proposed:** header + persisted membership only (already implemented in the draft).
- **Hybrid:** require both to agree (defense in depth), rejecting if
  `activeOrganizationId` disagrees with the header-resolved school. Adds complexity for
  marginal benefit if the header-based check is already authoritative.

## 5. Impact analysis

Behavior differs specifically for a session whose `activeOrganizationId` differs from
the organization implied by `X-School-Slug`. Need to confirm whether the web app ever
sends a school-slug header that doesn't match the session's active org (e.g. a user
switching schools without a full session refresh) — if so, this changes which
requests succeed.

## 6. Compatibility/rollout plan

No migration. Verify web client behavior: does it always keep `X-School-Slug` and
BetterAuth's active org in sync today? If yes, this is a no-op in practice and safe to
approve. If no, coordinate the client fix in the same rollout.

## 7. Acceptance criteria

Test: a session with `activeOrganizationId` set to School A, issuing a request with
`X-School-Slug` for School B where the user also has membership, is evaluated against
School B's permissions (not rejected, not evaluated against School A).
