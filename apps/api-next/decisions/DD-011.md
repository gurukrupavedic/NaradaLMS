# DD-011: Profile lifecycle and record retention (soft-delete)

**Status:** approved — all decisions below are confirmed human decisions (Revanth Pothukuchi, in
conversation, 2026-07-28 and 2026-08-02), not agent guesses. §9 records a deferred
admin-deactivation design that is approved to document now but not to implement in this pass.

## 1. Current behavior

`apps/api-next/src/profiles/repository.ts::deleteOwned` (called from `service.ts::deleteById`,
the only caller — verified by grep):

```ts
export async function deleteOwned(db: SchoolDb, id: string, userId: string): Promise<{ id: string }[]> {
  return db.delete(profile).where(and(eq(profile.id, id), eq(profile.userId, userId))).returning({ id: profile.id })
}
```

A physical `DELETE FROM profile`. `packages/db/src/schema/school.ts`'s FK graph off `profile.id`:

- `enrollment.profileId` → `ON DELETE cascade` — deleting a profile silently deletes every
  enrollment row referencing it (loses roster history with no trace).
- `exam.studentId` → `ON DELETE cascade` — deleting a student's profile deletes every exam
  scheduled for them.
- `evaluation.studentId` → `ON DELETE cascade` — same for evaluation-as-student.
- `evaluation.evaluatorId` → `ON DELETE restrict` — deleting a profile that has ever recorded a
  result as an evaluator is **blocked** (this is the exact case H7/DD-001 row 5 already fixed
  from a wrong 422 to a correct 409 "profile is still referenced by an evaluation and cannot be
  deleted").

So today: deleting a student-only profile silently destroys their exam/evaluation history;
deleting an evaluator profile is simply blocked with no path forward at all. Both are real
problems HARDENING_PLAN §14 exists to fix, and neither is a defensible "compatibility baseline"
worth preserving — this is destructive, role-dependent behavior with no product intent behind
it, not a deliberate design.

## 2. Problem/opportunity

Same as HARDENING_PLAN §14's own framing: physical delete is both destructive (loses
educational records that other stakeholders — instructors, program admins — may need) and
inconsistent (works for students, blocked for evaluators). §14.2 lists six sub-decisions this
note must settle.

## 3. The six DD-011 sub-decisions, answered

1. **Historical reports: retain the name, snapshot, or `"Deleted learner"`? Also: what about
   `phone`/`city`?** → **Retain all of it — name, phone, and city — unchanged. Confirmed
   directly by Revanth (2026-07-28 for phone/city, 2026-08-02 for name): none of these are
   treated as critical PII for this product's purposes, so there's no reason to clear or
   anonymize any of them on deactivation.** This overrides HARDENING_PLAN §14.1 step 3's
   suggested "clears phone and city" — that step was itself conditional on a privacy
   determination this note is now making explicitly, not a hardening requirement independent of
   product judgment. `softDeleteOwned` therefore only ever sets `deletedAt`; every other column
   on the row, including `name`/`phone`/`city`, is untouched by deactivation.
2. **Required retention period for exams/evaluations?** → **Indefinite; no automatic expiry.**
   No legal/product basis exists yet for a specific number (30 days? 7 years?), and
   HARDENING_PLAN gives none either. Retaining indefinitely by default and leaving deletion to a
   future, explicit, approved administrative operation is the conservative choice — data can
   always be purged later under a real policy; inventing a premature auto-expiry could destroy
   records a real retention policy would have wanted kept.
3. **Enrollment rows: deleted, or gain `endedAt`?** → **Neither — retained, completely
   untouched.** (Reversed from this note's first draft, which deleted them; see the correction
   below.) **Confirmed directly by Revanth**: the product wants to answer questions like "which
   batches was this user in?" and "what did they score in that batch?" even after the profile is
   deactivated. Deleting `enrollment` rows on deactivation would break the first question outright
   (`evaluation`/`exam` already carry `studentId` and, since H11, `batchId` directly, so the
   second question already survives regardless of what happens to `enrollment` — but "which
   batches" is answered by joining `enrollment` to `batch`, and there is no other record of that
   relationship). Pure soft-delete — touching only `profile.deletedAt` and leaving every other
   table alone — is both the simplest implementation and the one that actually satisfies this
   requirement.

   **Correction (this note's first draft got this wrong and reasoned itself into deleting
   history it didn't need to):** the original reasoning here leaned on PARITY_PLAN.md's note that
   *ordinary unenrollment* doesn't preserve history in this schema, and treated profile
   deactivation as "just another case of the same thing." Those are different situations —
   ordinary unenrollment is a person moving between batches while remaining active, and this
   codebase's general lack of an enrollment-history table is a separate, pre-existing gap, not a
   reason to *additionally* destroy a specific record on deactivation when the product explicitly
   wants that record kept.

   **This reversal opens one real gap that must be closed, not just "kept enrollment and moved
   on":** `apps/api-next/src/exams/repository.ts::findStudentEnrollmentForTrack` (the query
   `createExam` uses to confirm a student qualifies for a new exam) checks only `enrollment` and
   `batch` — never the target student's own `profile.deletedAt`. If a deactivated student's
   enrollment rows are left in place, that query would still say "yes, qualified," letting a new
   exam be scheduled against a deactivated profile — directly violating HARDENING_PLAN §14.1
   point 2 ("unusable for ... new enrollment, evaluation, or exam operations"). See §4.6 for the
   fix: the query now also joins `profile` and requires `profile.deletedAt IS NULL` for the
   target student.
4. **Undelete supported?** → **No, not in this pass.** Undelete needs its own decision (who can
   restore, what happens to relationships that changed in the meantime) — treating it as a
   separate follow-up keeps this change reviewable and doesn't block on answering a question
   nobody asked for yet.
5. **Who may perform administrative deactivation?** → **Only the profile's own owner, in this
   pass.** HARDENING_PLAN §1.2's own non-goals list "adding any route missing from the parity
   matrix" — an admin-deactivates-another-profile capability would be a *new* authorization
   surface/route, not a hardening fix to the existing one. This note only changes what `DELETE
   /profiles/:profileId` *does internally* (soft-delete instead of physical delete); it does not
   change who may call it. **Confirmed by Revanth (2026-08-02): an admin-deactivation capability
   is wanted eventually, so its design is sketched now in §9, but implementation is explicitly
   deferred to a later pass** — not built here.
6. **Legal erasure vs. ordinary deletion?** → **Not built in this pass.** Per §14.1 step 6,
   that's explicitly future, separate, audited work. This note's `deletedAt` mechanism is
   deactivation/deauthorization, not erasure — the row, its ID, its name, and now its contact
   fields and enrollment history all persist.

## 4. Proposed behavior

### 4.1 Schema (additive only, no FK changes)

Add nullable `profile.deletedAt: timestamp` to `packages/db/src/schema/school.ts`. No FK action
changes in this pass (`evaluation.evaluatorId`'s `ON DELETE restrict` etc. stay exactly as they
are per §14.3 step 5 — "change foreign-key actions in a later migration").

### 4.2 `profiles/repository.ts`

- New `softDeleteOwned(db: SchoolDb, id: string, userId: string): Promise<{ id: string }[]>` —
  `UPDATE profile SET deletedAt = now() WHERE id = ? AND userId = ? AND deletedAt IS NULL
  RETURNING id`. Only `deletedAt` is set — no other column changes (§3 point 1). The
  `deletedAt IS NULL` predicate makes a repeated delete match zero rows (idempotent-safe: the
  service treats "0 rows" as not-found, matching §14.4's "idempotent or an explicitly approved
  error" — the same 404 an unknown/foreign profile already returns, so a second delete attempt
  is indistinguishable from "already gone," leaking no extra information).
- `findByUserId` gains a `isNull(profile.deletedAt)` predicate, so `GET /profiles` stops listing
  a caller's own deactivated profiles.
- Remove `deleteOwned` (the old hard-delete) — confirmed by grep it has exactly one caller,
  `service.ts::deleteById`, which this note's §4.3 changes to use the new function instead. No
  dead code left behind.
- **No `deleteEnrollmentsForProfile` function** — enrollment rows are never touched by
  deactivation (§3 point 3, reversed from this note's first draft).

### 4.3 `profiles/service.ts::deleteById`

A single statement — no transaction needed, since deactivation is now exactly one write:

```ts
export async function deleteById(context: ProfileServiceContext, id: string): Promise<void> {
  const rows = await repository.softDeleteOwned(context.db, id, context.user.id)
  if (rows.length === 0) {
    throw notFound()
  }
}
```

(This note's first draft wrapped this in a transaction alongside an enrollment delete, and
caught its own ordering bug during planning — see git history for that correction. Both the
transaction and the ordering question are moot now that there is only one write.)

Same HTTP contract as today (204 on success via the unchanged route, 404 for missing/foreign/
already-deleted). `withConstraintMapping`'s H7 profile-in-use mapping stays defined (harmless,
now generically unreachable via this path since we never issue a raw `DELETE FROM profile` here
anymore — not removing it, since it's still semantically correct if any other/future code path
ever does issue a physical delete).

### 4.4 `naradaRoute.ts::resolveProfile` — "unusable for active request context"

Add `profile.deletedAt IS NULL` to the existing query predicate (or check
`profile.deletedAt !== null` after the fetch and treat it the same as "not found," i.e.
`forbidden()`, matching the existing foreign-profile branch). This is what satisfies §14.1 point
2 for the *acting* profile — every write in this codebase that requires a profile goes through
`resolveProfile` first (`profileRoute`), so centralizing the check here means batches/exams
create/update paths automatically reject a deactivated *caller* with no per-domain change
needed. It does **not** cover a deactivated profile used as a *target* (e.g. the student a new
exam is being scheduled for) — see §4.6.

### 4.5 What's explicitly NOT touched

- No change to `evaluation.evaluatorId`'s `ON DELETE restrict` or any other FK action (§14.3
  step 5, deferred).
- No admin-deactivates-another-profile endpoint (§3 point 5).
- No undelete endpoint (§3 point 4).
- No legal-erasure/PII-scrubbing operation (§3 point 6).
- No automatic retention-expiry job (§3 point 2).
- No change to `createProfile` — a user creating a new profile in a school where they
  previously had one soft-deleted just inserts a new row, exactly as today (the schema has no
  unique constraint on `profile.userId` forcing one-profile-per-user-per-school, so nothing
  breaks here; whether that *should* be constrained is a separate, unrelated question).
- `enrollment`, `exam`, `evaluation` rows belonging to a deactivated profile — untouched (§3
  point 3).

### 4.6 `exams/repository.ts::findStudentEnrollmentForTrack` — close the target-student gap

The query gains a join to `profile` and an added condition requiring the target student's
profile to be active:

```ts
export async function findStudentEnrollmentForTrack(
  db: SchoolDb,
  studentId: string,
  trackId: string,
): Promise<{ batchId: string }[]> {
  return db
    .select({ batchId: enrollment.batchId })
    .from(enrollment)
    .innerJoin(batch, eq(enrollment.batchId, batch.id))
    .innerJoin(profile, eq(enrollment.profileId, profile.id))
    .where(
      and(
        eq(enrollment.profileId, studentId),
        eq(enrollment.role, 'student'),
        eq(batch.trackId, trackId),
        isNull(profile.deletedAt),
      ),
    )
}
```

Without this, keeping `enrollment` rows intact on deactivation (§3 point 3) would silently let a
deactivated student still qualify for a brand-new exam, which is exactly what HARDENING_PLAN
§14.1 point 2 says must not happen. This is the one code change this reversal requires beyond
"stop deleting enrollment rows."

## 5. Alternatives

- **Baseline (no change):** keep physical delete. Rejected — actively destructive for students,
  a dead end for evaluators.
- **Anonymize the name (and/or phone/city) on delete:** considered and rejected — HARDENING_PLAN's
  own recommended alternative doesn't call for it, doing so wouldn't properly satisfy a real
  erasure requirement anyway (that needs its own audited path), and name/phone/city are all
  confirmed not to be critical PII for this product (§3 point 1).
- **Delete enrollment rows on deactivation (this note's original choice):** rejected on reversal
  — breaks "which batches was this user in," which the product explicitly wants to keep
  answering. See §3 point 3's correction.
- **Add `enrollment.endedAt` instead of retaining rows as-is:** considered as a middle ground
  (mark enrollment ended without deleting it) and rejected as unnecessary — nothing currently
  needs to distinguish "actively enrolled" from "enrolled, but the profile is now deactivated";
  joining to `profile.deletedAt` (§4.6) already gives every consumer that needs "is this student
  currently usable" answer without a new column.
- **Proposed:** pure soft-delete — touch only `profile.deletedAt`; leave `phone`, `city`,
  `enrollment`, `exam`, and `evaluation` completely alone; close the one resulting gap in exam
  assignment qualification.

## 6. Impact analysis

- Affects `DELETE /profiles/:profileId` (behavior changes from destructive-cascade-or-blocked to
  a single-column soft-delete), `GET /profiles` (excludes the caller's own deactivated profiles),
  every `profileRoute`-gated write (a deactivated profile can no longer be used as the active
  `X-Profile-Id`), and `POST /exams` (a deactivated student can no longer be the target of a new
  exam, per §4.6).
- **No HTTP status/response-shape change** — `DELETE /profiles/:profileId` still returns an empty
  204 on success and 404 for missing/foreign/already-deleted, exactly as today.
- Real behavior change worth flagging: an evaluator profile that was previously **permanently
  blocked** from deletion (409) can now be deactivated successfully — a genuine new capability,
  not just a bug fix. **Confirmed intentional by Revanth (2026-08-02):** the old 409 block was a
  side effect of physical `DELETE` tripping `evaluation.evaluatorId`'s `ON DELETE restrict`, not
  a deliberate policy — since soft-delete no longer risks losing evaluation history, there is no
  remaining reason to keep evaluators locked out of deactivating themselves.
- Historical reads are fully preserved: `GET`-style queries against `enrollment`/`exam`/
  `evaluation` for a deactivated profile return exactly what they would have before deactivation
  — nothing is deleted, nothing is anonymized.
- No schema/migration impact on `apps/api/src` — only `apps/api-next`'s path changes.
  `profile.deletedAt` is a new nullable column; existing rows are unaffected (`NULL` = active).

## 7. Acceptance criteria

Matching HARDENING_PLAN §14.4 concretely:

- `DELETE /profiles/:profileId` on an active profile the caller owns: 204, `profile.deletedAt`
  set, `name`/`phone`/`city` unchanged, every `enrollment`/`exam`/`evaluation` row referencing
  the profile untouched.
- Repeating the same delete: 404 (idempotent-safe, matches the existing not-found response for
  an unknown profile).
- `GET /profiles` for the owning user no longer lists the deactivated profile.
- A deactivated profile supplied as `X-Profile-Id` on any `profileRoute`-gated request: rejected
  the same way a foreign/nonexistent profile is today (403 via `resolveProfile`'s existing
  branch).
- A deactivated student can no longer be the target of a newly created exam (422 via
  `assertValidExamAssignment`, the same "not enrolled" message a never-enrolled student gets —
  their stale enrollment row exists but no longer qualifies).
- An evaluator profile (previously undeletable, 409) can now be deactivated successfully; its
  past evaluations remain queryable with the evaluator's name intact.
- A student profile's exams/evaluations/enrollments all survive deactivation unchanged.

## 9. Deferred: admin-deactivation design sketch (not implemented in this pass)

Approved to document now, per §8 point 2 above; implementation is separate future work, its own
follow-up task, not part of this commit.

**Actor:** a user holding an admin/owner role on the organization (`member.role`, public schema)
for the school the target profile belongs to — not merely any authenticated user, and not
restricted to the target's own profile owner. Needs a defined role check; today's codebase has no
precedent for an admin-acts-on-another-user's-resource path in `apps/api-next`, so this would be
the first of its kind and should be scoped narrowly (this one operation) rather than as a general
"admin can do X on behalf of Y" mechanism.

**Route:** a new endpoint, not a parameter added to the existing owner-only
`DELETE /profiles/:profileId` — reusing that route for a different actor would conflate two
different authorization checks (self vs. admin-on-behalf-of) behind one path and one set of
error semantics. Candidate shape: `DELETE /schools/:schoolId/profiles/:profileId` or similar,
gated by an admin/owner role check against `member` before ever touching `profile`.

**Mechanism:** identical to `softDeleteOwned` minus the `userId` predicate — i.e. a new
`repository.softDeleteById(db, id)` that only requires `deletedAt IS NULL`, called from a new
service function that performs the role check first. No new schema, no new columns; this reuses
`profile.deletedAt` exactly as owner-deactivation does.

**Open questions to resolve before implementing** (not answered here — surfacing them is the
point of documenting this now rather than silently deferring):
- Should the target profile's owner be notified when an admin deactivates it on their behalf?
- Does this need its own audit trail (who deactivated it, when, as distinct from `deletedAt`
  alone), given it's now a third party acting on someone else's record?
- Should a super-admin (cross-school) be able to do this, or only an admin of that specific
  school?
