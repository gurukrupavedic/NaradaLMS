# DD-007: Let public routes ignore an unrelated invalid `X-School-Slug`

**Status:** proposed

## 1. Current behavior

Per PARITY_PLAN.md §3.2, `/health`, `/profile`, `/schools`, and BetterAuth routes are
supposed to require no school lookup at all in the current backend's contract. It is not
yet confirmed whether the current backend errors if a caller sends a garbage/unknown
`X-School-Slug` header on one of these routes anyway (i.e., does an irrelevant header
value ever get validated on a route that doesn't need it?).

## 2. Problem/opportunity

If the current backend silently ignores `X-School-Slug` on these routes, but the draft's
route wrappers (`publicRoute` etc., PARITY_PLAN.md §3.2) end up resolving school for
every request regardless of route, an unrelated/malformed header would incorrectly 400 or
404 a request to a route that has nothing to do with any school.

## 3. Proposed behavior

`publicRoute` (and any route that doesn't need a school) never reads or validates
`X-School-Slug`, even if present and garbage. Only `schoolRoute`/`userRoute`/
`profileRoute` resolve and validate it.

## 4. Alternatives

- **Baseline:** replicate whatever the current backend actually does today (needs to be
  checked directly against `apps/api/src` — the plan flags this as unverified, not
  confirmed-different).
- **Proposed:** structural guarantee via route-wrapper design (`publicRoute` never
  touches the header) — this is arguably not even a "behavior change" but a natural
  consequence of the wrapper split in PARITY_PLAN.md §3.2, so it may not need the full
  DD process once §3.2's wrapper redesign itself is implemented.

## 5. Impact analysis

Low risk either way — this only matters for callers sending a school-slug header to a
route that shouldn't care, which is not a normal client path. Mainly a robustness/defense
question.

## 6. Compatibility/rollout plan

No rollout coordination needed. Resolve as part of Phase 1's route-wrapper
implementation (PARITY_PLAN.md §3.2); no separate migration.

## 7. Acceptance criteria

Test: `GET /health`, `GET /profile`, `GET /schools` with a garbage or nonexistent
`X-School-Slug` header all succeed identically to a request with no such header.

## 8. Manual approval record

_Pending._ Likely low-friction to approve since it's closer to "implement the wrapper
split correctly" than an actual behavior trade-off — worth confirming with a quick check
against `apps/api/src` before treating it as a real design fork.
