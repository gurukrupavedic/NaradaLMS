# DD-007: Let public routes ignore an unrelated invalid `X-School-Slug`

**Status:** approved — deliberate deviation from the verified current baseline (see §1, §8)

## 1. Current behavior

**Verified directly against `apps/api/src`, 2026-08-28 (supersedes this section's original
"not yet confirmed" framing):** `apps/api/src/routes/index.ts` mounts `resolveDb` (the
school-resolution middleware) via `router.use(resolveDb)` **before** `/schools` and `/profile`
are mounted — both go through it. `resolveDb` (`apps/api/src/middlewares/school.ts`): if
`X-School-Slug` is absent, it sets a `public` context and proceeds; but if the header **is
present and doesn't match any school, it throws `notFound()` — a real 404**, even though
`/schools` and `/profile` don't semantically need a school. Only `/health` (mounted before
`resolveDb` in `routes/index.ts`) and `/auth/*splat`/`/auth/phone-number/send-otp` (mounted in
`server.ts` before `setupRoutes` even runs) actually skip school resolution entirely.

So the current backend does **not** ignore an invalid `X-School-Slug` on `/profile` or
`/schools` — it 404s. `PARITY_PLAN.md` §3.2's stated target ("No school lookup on `/health`,
`/profile`, `/schools`, or BetterAuth routes") was itself already wrong about `/profile` and
`/schools`, not just this note's premise.

## 2. Problem/opportunity

If the current backend silently ignores `X-School-Slug` on these routes, but the draft's
route wrappers (`publicRoute` etc., PARITY_PLAN.md §3.2) end up resolving school for
every request regardless of route, an unrelated/malformed header would incorrectly 400 or
404 a request to a route that has nothing to do with any school.

## 3. Proposed behavior

`publicRoute` (and any route that doesn't need a school) never reads or validates
`X-School-Slug`, even if present and garbage. Only `schoolRoute`/`userRoute`/
`profileRoute` resolve and validate it.

## 4. Alternatives

- **Baseline:** replicate whatever the current backend actually does today (needs to be
  checked directly against `apps/api/src` — the plan flags this as unverified, not
  confirmed-different).
- **Proposed:** structural guarantee via route-wrapper design (`publicRoute` never
  touches the header) — this is arguably not even a "behavior change" but a natural
  consequence of the wrapper split in PARITY_PLAN.md §3.2, so it may not need the full
  DD process once §3.2's wrapper redesign itself is implemented.

## 5. Impact analysis

Low risk either way — this only matters for callers sending a school-slug header to a
route that shouldn't care, which is not a normal client path. Mainly a robustness/defense
question.

## 6. Compatibility/rollout plan

No rollout coordination needed. Resolve as part of Phase 1's route-wrapper
implementation (PARITY_PLAN.md §3.2); no separate migration.

## 7. Acceptance criteria

Test: `GET /health`, `GET /profile`, `GET /schools` with a garbage or nonexistent
`X-School-Slug` header all succeed identically to a request with no such header.

## 8. Manual approval record

**Approved by Revanth Pothukuchi, 2026-08-28**, in conversation, after the §1 verification
above showed this is a real behavior change, not a no-op: chose the original "Proposed"
alternative in §4 (`publicRoute` never reads/validates `X-School-Slug`, even if present and
garbage) **over** matching the verified current baseline (validate + 404 on `/schools` and
`/profile`). This is a deliberate, approved deviation from compatibility-baseline replication —
record it in `PARITY_PLAN.md`'s route matrix/§3.2 as an intentional target-behavior change, not
an oversight, since the old backend's 404-on-garbage-header behavior for routes that don't need
a school was itself accidental coupling from mount order, not a documented contract.
