# DD-012: Persist assessment batch context

**Status:** approved (agent decision, pending human review — see §8). **Scoped narrower than
HARDENING_PLAN §15 asks for — this note implements only the parts safe to do without real
production data. See §3's explicit scope cut.**

## 1. Current behavior

`packages/db/src/schema/school.ts`: `exam` stores `chapterId` and `studentId` but no `batchId`;
`evaluation` stores `studentId`, `chapterId`, `evaluatorId` but no `batchId`. Neither table
references `batch` at all.

`apps/api-next/src/exams/repository.ts::findStudentEnrollmentForTrack` (the query behind the
"is this student enrolled in a qualifying batch for this chapter's track" check used by
`createExam`):

```ts
export async function findStudentEnrollmentForTrack(db, studentId, trackId) {
  return db
    .select({ batchId: enrollment.batchId })
    .from(enrollment)
    .innerJoin(batch, eq(enrollment.batchId, batch.id))
    .where(and(eq(enrollment.profileId, studentId), eq(enrollment.role, 'student'), eq(batch.trackId, trackId)))
    .limit(1)
}
```

**Real, already-present bug, found while reading this for H11:** the `.limit(1)` means this
query returns at most one row *regardless of how many batches actually qualify*. `service.ts`'s
`assertValidExamAssignment` then only checks `enrolled.length === 0` (reject) vs. non-zero
(accept) — it can never observe or reject the case where a student is enrolled as `student` in
**two or more** batches on the same track. Today's code silently proceeds using whichever
candidate the database happens to return first, with no defined ordering — exactly the "select
an arbitrary candidate" anti-pattern HARDENING_PLAN §15.3's own backfill instructions explicitly
warn against ("Never select an arbitrary candidate with `limit 1`"), except this is in the live
write path, not just the backfill. This is precisely the risk HARDENING_PLAN §15.4's acceptance
criterion "a multi-batch student cannot create an ambiguous exam/evaluation" targets — and today,
they can.

## 2. Problem/opportunity

Two distinct problems, worth separating because only one is safely fixable right now:

1. **The multi-batch ambiguity bug (§1)** — fixable today, no data migration, no production data
   needed to reason about it: remove the `.limit(1)`, actually count candidates, reject 0 *and*
   >1, accept exactly 1.
2. **The historical-context-drift problem HARDENING_PLAN §15 is really about** — an exam/
   evaluation's authorization is currently re-derived from the student's *current* enrollment
   every time it's read, so moving or removing that enrollment retroactively changes which
   batch a historical assessment appears to belong to (or makes it disappear from a batch's view
   entirely). Fixing this needs `batchId` stored at creation time **and** a backfill of every
   existing exam/evaluation row **and** a multi-stage rollout (HARDENING_PLAN §15.3 lists 9
   steps: nullable columns → backfill → zero/multi-candidate manual resolution → dual-read
   diagnostics → switch reads → non-null). Steps 2–4 and 8–9 need real production data (to find
   which existing rows have zero or multiple candidate batches and decide each one by hand) that
   I have no access to and no authorization to guess at with a `LIMIT 1`-style shortcut — doing
   so would repeat the exact mistake this note exists to fix, just against real historical data
   instead of new writes.

## 3. Proposed behavior — explicit scope cut

**In scope for this pass (safe without production data access):**

- Add nullable `exam.batchId` / `evaluation.batchId`, referencing `batch.id`, per HARDENING_PLAN
  §15.1. New rows only; existing rows get `NULL` (HARDENING_PLAN §15.3 step 1, exactly).
- Add an index on `(batchId, studentId)` on both tables per §15.1.
- Fix the `.limit(1)` ambiguity bug in `findStudentEnrollmentForTrack` (§1) — this is correct and
  needed regardless of the backfill question, since it's a live-write-path correctness bug, not
  a historical-data question.
- `createExam` captures the resolved (now-guaranteed-unique) `batchId` and stores it on the new
  `exam` row (§15.2 bullet 1).
- `recordExamResult` copies the exam's stored `batchId` onto the new `evaluation` row it inserts
  (§15.2 bullet 3 — "an evaluation created from an exam copies the exam's batch ID"). This needs
  no new lookup: the exam row already has `batchId` once it's stored.
- Qualification (finding the one qualifying batch) stays a guarded read inside the same
  create-exam flow it's already part of, not a separate precheck-only path (§15.2 bullet 5) —
  no change needed here, `assertValidExamAssignment` already runs immediately before the insert
  in the same service call, not as a separate, racy precheck. (A true race — two concurrent
  requests each seeing zero conflicting batches, both inserting — is a distinct concern from the
  ambiguity bug this note fixes, and is out of scope here; note it in §5.)

**Explicitly OUT of scope for this pass — HARDENING_PLAN §15.3 steps 2–9:**

- **No backfill of existing rows.** I have no access to real production data and no way to
  responsibly resolve the zero-candidate and multi-candidate cases §15.3 steps 2–4 require
  without seeing it — guessing here would be the exact `LIMIT 1` mistake this note fixes,
  applied to historical data instead of new writes, which is worse (historical data can't be
  regenerated).
- **No dual-read diagnostics, no switch of authorization/reads to stored `batchId`** (§15.3
  steps 5, 8) — until existing rows are backfilled, most historical exams/evaluations would have
  `batchId = NULL`, so switching reads to rely on it now would break every pre-existing record.
  Authorization keeps deriving from current enrollment, exactly as today, for this pass.
- **No `NOT NULL` constraint** (§15.3 step 9) — correctly gated on backfill completion, which
  hasn't happened.
- **No "direct evaluation creation" batch selection** (§15.2 bullet 2) — that endpoint
  (`POST /batches/:batchId/evaluations`) doesn't exist in `apps/api-next` yet (confirmed: no
  `evaluations` domain exists; it's still-unbuilt parity work per `PARITY_PLAN.md` §10). Nothing
  to change here until that domain is built — when it is, it should select and store `batchId`
  the same way `createExam` now does.

This means HARDENING_PLAN §15.4's own acceptance criteria are only **partially** met by this
pass: "a multi-batch student cannot create an ambiguous exam/evaluation" — met. "Every migrated
record has a documented batch source" and "an educator is authorized only through the
assessment's stored batch" — **not yet**, deliberately, pending the backfill this pass doesn't
attempt.

## 4. Alternatives

- **Do the full 9-step rollout now, inventing backfill resolution rules:** rejected — the whole
  point of §15.3's caution is that zero/multi-candidate historical rows need a human to look at
  real data and decide; inventing a rule (e.g. "pick the most recent enrollment") reproduces the
  arbitrary-selection problem against data that can't be regenerated if the guess is wrong.
- **Skip the schema change entirely until a backfill plan exists:** rejected — the nullable
  column and the new-row write-path fix are safe, valuable now on their own (they stop the
  problem from getting worse with every new exam/evaluation created while backfill planning
  happens later), and HARDENING_PLAN §15.3 explicitly sequences them as step 1 before backfill.
- **Fix only the `.limit(1)` bug, skip the schema change:** rejected — the ambiguity fix and the
  `batchId` column are both called for by HARDENING_PLAN §15 and naturally land together (the
  ambiguity check is what makes storing a single, unambiguous `batchId` meaningful).
- **Proposed:** schema + write-path only (§3), explicitly stopping short of backfill/read-path
  changes, with the stopping point and reasoning recorded here for whoever picks up the backfill
  with real data access.

## 5. Impact analysis

- Affects `packages/db/src/schema/school.ts` (additive columns + indexes, no FK action changes,
  no `NOT NULL`), `apps/api-next/src/exams/repository.ts` (`findStudentEnrollmentForTrack`'s
  `.limit(1)` removed; new `insert`/`insertEvaluation` calls include `batchId`),
  `apps/api-next/src/exams/service.ts` (`assertValidExamAssignment` now also rejects >1
  candidates; `createExam`/`recordExamResult` thread the resolved `batchId` through).
- **Real behavior change**: a student enrolled as `student` in two-or-more batches on the same
  track, who could previously have an exam silently created against an arbitrary one of them,
  now gets a 422 instead. This is the intended fix, not a side effect — but it's a new rejection
  case worth knowing about (a student legitimately in two batches on the same track, however rare,
  now can't have an exam scheduled at all without a product decision on how to disambiguate,
  e.g. requiring an explicit `batchId` in the request body — out of scope here, since
  HARDENING_PLAN §15.2 doesn't ask for a request-schema change in this note, only "an explicit
  qualifying batchId" being *selected*, which for now still means "the one that exists").
- No response/HTTP contract change: `exam`/`evaluation` rows aren't projected through a schema
  that would newly expose `batchId` (need to confirm during implementation whether the response
  schema is a full-row passthrough, matching DD-013's earlier finding that `ExamSchema` is never
  re-parsed on output — if so, `batchId` would start appearing in `GET /exams` responses simply
  by existing as a column, since routes serialize repository rows directly; decide during
  implementation whether to add a response-level exclusion, matching DD-011's `profileColumns`
  precedent, or whether exposing `batchId` in exam responses is harmless/desirable — HARDENING_
  PLAN doesn't say to hide it, unlike `profile.deletedAt`, so I'm treating an exposed `batchId` on
  `GET /exams`/`GET /exams/:id` as acceptable rather than adding a project-out step; flag this for
  review since it IS a response-shape addition, unlike every other field this note touches).
- A true concurrent-race variant (two simultaneous exam creations for a student whose single
  qualifying batch is being concurrently removed) is not hardened further by this note — the
  existing precheck-then-insert shape stays as it is elsewhere in this file; HARDENING_PLAN §15.2
  bullet 5's "not the only protection" language is satisfied by inserting immediately after the
  check within one service call, not by adding new row-locking, which would be new scope.

## 7. Acceptance criteria

- `findStudentEnrollmentForTrack` returns every qualifying batch, not just the first one found
  (no `.limit`).
- `createExam` for a student with zero qualifying batches: 422 (unchanged message/behavior).
- `createExam` for a student with exactly one qualifying batch: succeeds, the new exam row's
  `batchId` matches that batch.
- `createExam` for a student with two or more qualifying batches on the same track: 422 with a
  distinct "ambiguous" message (new).
- `recordExamResult`'s inserted evaluation row has the same `batchId` as the exam it's recording
  a result for.
- Existing exams/evaluations (pre-migration) have `batchId = NULL` and are otherwise unaffected
  — no read path in this pass changes behavior for them.
- The multi-batch-ambiguity tests can be written and pass today as unit/mock-level tests (no
  real DB needed, same pattern already established for `exams/service.test.ts`).
