# DD-015: Tenant connection-pool budget, timeouts, and lifecycle

**Status:** approved (agent decision, pending human review — see §8). **This note carries more
uncertainty than the others I've drafted — the connection-budget numbers below are placeholder
assumptions, not verified operational facts. See §3's explicit flag.**

## 1. Current behavior

`packages/db/src/index.ts`, verified directly:

- `publicPool = new Pool({ connectionString: env.DATABASE_URL, options: '-c search_path=public' })`
  — no `max`, `idleTimeoutMillis`, `connectionTimeoutMillis`, `statement_timeout`, or
  `maxLifetimeSeconds`. node-postgres (`pg@8.21.0`) defaults: `max: 10`, `idleTimeoutMillis:
  10000`, `connectionTimeoutMillis: 0` (**no acquisition timeout at all** — a caller waiting for
  a pool slot can hang forever), no statement timeout, no max lifetime.
- `getSchoolDb(organizationId)` creates a `new Pool({ connectionString: env.DATABASE_URL, options:
  '-c search_path=...' })` per school, identically unconfigured, cached in an `LRUCache` with
  `max: 100` (`MAX_DB_CACHE_SIZE`, hardcoded).
- Worst case today: `10` (public) `+ 100 cached schools × 10` (school pool default) `= 1010`
  connections **per process**, before any horizontal scaling — this is the exact number
  HARDENING_PLAN §13 opens with ("near 1,000 connections per process").
- **A real, unrelated-but-adjacent bug found while reading this code for H9**: neither pool has
  an `'error'` event listener attached. `pg.Pool` extends `EventEmitter`, and node.js's
  `EventEmitter` has special-cased behavior for the `'error'` event: if a client already
  connected to the pool has an unrelated error (e.g. the database terminates an idle
  connection, a network blip), the pool emits `'error'` — and **with zero listeners attached, an
  `'error'` event throws, crashing the entire Node process** (this is a well-documented
  node-postgres gotcha, not a hypothetical). Today, a single idle-connection hiccup on any
  cached school pool (or the public pool) can take down the whole API process. Fixing this is a
  one-line-per-pool addition and squarely within H9's "expose or log" observability requirement
  (§13.2), so I've included it (see §3).
- `dbCache`'s `dispose` callback does `closePool(entry.pool).catch(() => {})` — fire-and-forget,
  not tracked anywhere. `shutdownPools` awaits `closePool(publicPool)` plus `closePool` for every
  pool **currently in the cache**, but has no way to know about or await a pool that was just
  evicted (LRU eviction on `.set()` when the cache is full) and is mid-close via `dispose`. A
  shutdown racing an eviction can exit before that pool's `pool.end()` resolves.
- `apps/api-next/src/health/route.ts`'s `GET /ready` does `await db.execute(sql\`select 1\`)` with
  no timeout at all — a dead/unreachable database makes this hang until whatever the underlying
  TCP stack eventually gives up (OS-dependent, typically minutes), not "within the deadline" per
  HARDENING_PLAN §13.3's explicit acceptance criterion.
- No pool-count/client-count observability exists anywhere; `pg.Pool` natively exposes
  `.totalCount`/`.idleCount`/`.waitingCount`/`.expiredCount` getters, none of which are read.

## 2. Problem/opportunity

Three real risks, in descending order of how confident I am they're worth fixing regardless of
the exact numbers in §3:

1. **Crash risk (highest confidence, no ops data needed to justify)**: the missing `'error'`
   listener can crash the process on an ordinary transient connection error. This is a
   correctness bug independent of pool sizing.
2. **Hung shutdown / hung readiness (high confidence)**: no acquisition timeout, no readiness
   deadline, untracked eviction promises — all three make "hang instead of fail cleanly" the
   current behavior in exactly the scenarios HARDENING_PLAN §13.3 tests for.
3. **Connection-budget overrun (real, but the specific numbers are genuinely unknowable without
   ops input)**: today's worst case (~1010/process) is unconfigured, not validated against any
   budget. I do not have access to production `max_connections`, instance count, or a connection
   proxy's presence — HARDENING_PLAN §3.1's own audit requires operational data I cannot obtain
   in this environment. I'm making this configurable with conservative-by-default limits rather
   than asserting specific "correct" numbers.

## 3. Proposed behavior

### 3.1 New validated env vars (`packages/env/src/index.ts`), all optional with defaults

Added to the existing `server` schema, additive only (every existing var untouched):

```ts
DB_PUBLIC_POOL_MAX: z.coerce.number().int().positive().default(5),
DB_SCHOOL_POOL_MAX: z.coerce.number().int().positive().default(3),
DB_SCHOOL_POOL_CACHE_MAX: z.coerce.number().int().positive().default(10),
DB_ACQUIRE_TIMEOUT_MS: z.coerce.number().int().positive().default(5_000),
DB_IDLE_TIMEOUT_MS: z.coerce.number().int().positive().default(30_000),
DB_STATEMENT_TIMEOUT_MS: z.coerce.number().int().positive().default(30_000),
DB_MAX_LIFETIME_SECONDS: z.coerce.number().int().nonnegative().default(0), // 0 = disabled (pg's own default)
DB_READY_TIMEOUT_MS: z.coerce.number().int().positive().default(3_000),
```

**Explicit flag (do not skip this when reviewing):** I do not know this deployment's real
PostgreSQL `max_connections`, its reserved-connections setting, how many application instances
run concurrently, whether a connection proxy (PgBouncer etc.) sits in front of Postgres, or how
many schools are concurrently active in practice. HARDENING_PLAN §3.1 requires recording all of
these before approving a specific budget — I could not perform that audit in this environment.
The numbers above are chosen to be **conservative defaults that are safer than today's
unconfigured state** (node-postgres's own default `max: 10` per pool, applied to up to 100 cached
schools, is what created the ~1000-connection worst case), not numbers I've validated against a
real budget. Using HARDENING_PLAN §3.1's formula:

```
public pool maximum + application instances × cached school pools × school-pool maximum
≤ 70% of usable PostgreSQL connections
```

With this note's defaults (`5 + instances × 10 × 3`) and an *assumed* single instance and an
*assumed* PostgreSQL `max_connections` of 100 (a common small/managed-Postgres default — e.g.
the local `docker-compose.yaml` in this repo doesn't override it): `5 + 1×10×3 = 35`, comfortably
under `70` (70% of 100). **This assumption breaks down quickly with more than ~2 instances at
this same `max_connections`** — `2 × 35 = 70`, exactly the boundary; 3+ instances would exceed
it. Whoever reviews this must plug in the real instance count and `max_connections` and adjust
`DB_SCHOOL_POOL_CACHE_MAX`/`DB_SCHOOL_POOL_MAX` (env vars, no code change needed) accordingly —
this is precisely why these are configuration, not hardcoded.

### 3.2 Apply the config in `packages/db/src/index.ts`

- `publicPool`: add `max: env.DB_PUBLIC_POOL_MAX`, `idleTimeoutMillis: env.DB_IDLE_TIMEOUT_MS`,
  `connectionTimeoutMillis: env.DB_ACQUIRE_TIMEOUT_MS`, `statement_timeout:
  env.DB_STATEMENT_TIMEOUT_MS`, `maxLifetimeSeconds: env.DB_MAX_LIFETIME_SECONDS` (all verified
  as real `pg.Pool`/`pg.Client` constructor options in the installed `pg@8.21.0`/`pg-pool@3.14.0`
  — `statement_timeout` and `maxLifetimeSeconds` are not npm-doc-obvious but are read directly by
  `pg-pool`'s and `pg`'s source, confirmed by reading `node_modules/.pnpm/pg-pool@3.14.0.../
  index.js` and `node_modules/.pnpm/pg@8.21.0/node_modules/pg/lib/client.js`).
- `getSchoolDb`'s per-school `new Pool({...})`: same five options, using `DB_SCHOOL_POOL_MAX`
  instead of `DB_PUBLIC_POOL_MAX`.
- `dbCache = new LRUCache({ max: env.DB_SCHOOL_POOL_CACHE_MAX, ... })` — replaces the hardcoded
  `MAX_DB_CACHE_SIZE = 100`.
- **Attach an `'error'` listener to every pool the moment it's created** (both `publicPool` and
  each school pool inside `getSchoolDb`): `pool.on('error', err => console.error('pg pool error',
  { schoolId: organizationId /* omitted for publicPool */, message: err.message }))`. This is
  the fix for §1's crash bug. Never log `err` itself unfiltered (could contain a connection
  string in some driver error paths) — log `err.message` only, matching §13.2's "without
  credentials or connection strings."

### 3.3 Track eviction promises for `shutdownPools`

```ts
const closingPools = new Set<Promise<void>>()

const dbCache = new LRUCache<string, CachedDb>({
  max: env.DB_SCHOOL_POOL_CACHE_MAX,
  dispose: (entry, key) => {
    console.warn('closing evicted school database pool', { schoolId: key })
    const closing = closePool(entry.pool)
    closingPools.add(closing)
    // The `.catch` must sit at the END of the chain, not on `closing` itself: `.finally()`
    // returns a NEW promise that re-rejects if `closing` rejects, and leaving THAT one
    // unhandled crashes the process on a failing pool.end() — the exact class of bug this
    // note exists to fix. `closing` itself stays unswallowed so shutdownPools' allSettled
    // below can still observe and aggregate a real close failure.
    closing.finally(() => closingPools.delete(closing)).catch(() => {})
  },
})

export async function shutdownPools(): Promise<void> {
  const cachedPools = [...dbCache.values()].map(entry => entry.pool)
  dbCache.clear() // stop new callers from getting a pool we're about to close
  const results = await Promise.allSettled([
    closePool(publicPool),
    ...cachedPools.map(pool => closePool(pool)),
    ...closingPools, // pools evicted and mid-close before shutdown began
  ])
  // ...unchanged failure-aggregation logic
}
```

**Correction (caught during planning, not in the original draft of this note):** the first
version of this snippet put `.catch(() => {})` nowhere, matching a plausible reading of "just
track the promise." Verified empirically (node 22.13.1): `closePool(entry.pool).finally(() =>
closingPools.delete(closing))` with no further handling leaves the `.finally()`-derived promise's
rejection unhandled whenever the evicted pool's `.end()` fails, which crashes the process on an
unhandled rejection — the same failure class §1's `'error'`-listener fix addresses. The `.catch`
must terminate the chain *after* `.finally()`, and it must NOT be attached to `closing` itself
(that would swallow the rejection before `Promise.allSettled` in `shutdownPools` gets a chance to
observe it for aggregation). `closePool` is already idempotent (checks the `closedPools`
`WeakSet` before calling `pool.end()`), so a pool that's both still-cached and mid-eviction-close
(a narrow race) is still only ended once.

### 3.4 Readiness deadline

`apps/api-next/src/health/route.ts`'s `/ready` handler wraps the existing check in a timeout
race:

```ts
router.get(
  '/ready',
  publicRoute(async ({ res, db }) => {
    const timeout = new Promise<never>((_, reject) =>
      setTimeout(() => reject(new Error('readiness check timed out')), env.DB_READY_TIMEOUT_MS),
    )

    try {
      await Promise.race([db.execute(sql`select 1`), timeout])
    } catch {
      res.status(503).json({ status: 'not ready', checks: { database: 'down' } })
      return
    }

    res.status(200).json({ status: 'ready', checks: { database: 'up' } })
  }),
)
```

(Requires importing `env` from `@narada/env` in `health/route.ts`, which already has this
dependency transitively via `@narada/db`.) A dead database now fails within
`DB_READY_TIMEOUT_MS` (default 3s) instead of hanging on the OS's TCP timeout. Note: the
`Promise.race`'s losing `db.execute` call is not cancelled (the `pg` driver has no cancellation
token for an in-flight query from the client side) — it continues running in the background
and its eventual resolution/rejection is simply ignored. This matches "fail within the deadline
rather than hang" without requiring query cancellation, which is a larger feature or would need
a `pg` `Client`-level `.query(..., { signal })`-style API not consistently available in this
driver version.

### 3.5 Minimal observability

Add one exported function to `packages/db/src/index.ts`:

```ts
export function getPoolStats(): {
  public: { total: number; idle: number; waiting: number }
  cachedSchools: number
  schools: { total: number; idle: number; waiting: number }
} {
  const schoolPools = [...dbCache.values()].map(entry => entry.pool)
  return {
    public: {
      total: publicPool.totalCount,
      idle: publicPool.idleCount,
      waiting: publicPool.waitingCount,
    },
    cachedSchools: dbCache.size,
    schools: {
      total: schoolPools.reduce((sum, p) => sum + p.totalCount, 0),
      idle: schoolPools.reduce((sum, p) => sum + p.idleCount, 0),
      waiting: schoolPools.reduce((sum, p) => sum + p.waitingCount, 0),
    },
  }
}
```

This satisfies §13.2's "cached school-pool count" and "total/open/idle/waiting clients per pool
or in aggregate" as a queryable function. I'm **not** wiring this into an HTTP endpoint or a
metrics exporter (Prometheus etc.) — no such infrastructure exists in this repo today (no
`prom-client` dependency, no metrics route), and adding one is a larger, separate infrastructure
decision outside a "make the existing pool honest" hardening pass. `getPoolStats()` is available
for `GET /health/ready` to optionally include, or for a future metrics integration to call — I've
left it unwired to keep this change's blast radius to `packages/db` plus the one readiness-route
edit in §3.4.

Acquisition-timeout and eviction/creation *counts* (also requested by §13.2) are logged, not
counted: the `'error'` listener from §3.2 logs pool errors as they happen (`console.error`), and
I'm adding one more `console.warn` at pool creation (`getSchoolDb`, only on a cache miss) and one
at eviction (inside `dispose`) with the school id. Turning "log lines" into "counters" needs a
metrics backend this repo doesn't have yet — logging is the honest minimum that satisfies "expose
**or** log" without inventing infrastructure.

## 4. Alternatives

- **Baseline (no change):** leave pools unconfigured. Rejected — the `'error'`-listener crash
  risk alone is worth fixing regardless of the sizing question, and "no acquisition timeout, no
  readiness deadline" are correctness bugs independent of the exact budget numbers.
- **Hardcode "correct" numbers now:** rejected — I don't have the operational data HARDENING_PLAN
  §3.1 requires to pick real numbers, and hardcoding invented numbers with false confidence would
  be worse than configuration with clearly-flagged placeholder defaults.
- **Add a full metrics/APM integration (Prometheus, OpenTelemetry) as part of this note:**
  rejected as disproportionate scope — no such infrastructure exists in this repo; that's a
  separate infrastructure decision, not a hardening fix to existing (mis)configuration.
- **Proposed:** validated, conservative-default configuration for every knob HARDENING_PLAN §13.1
  lists; fix the `'error'`-listener crash bug found along the way; track eviction promises; add a
  readiness deadline; expose pool stats as a plain function; log (not count) lifecycle events.

## 5. Impact analysis

- `packages/db` and `packages/env` both change — shared with `apps/api` (old backend) and
  `apps/web`/`tools` (env schema only). All new env vars are optional with defaults, so neither
  consumer needs any change or new configuration to keep working.
- **Real behavior change, needs a deploy-time check**: pools now have a `max` of 3–5 instead of
  node-postgres's implicit default of 10, and an acquisition timeout of 5s instead of none. If
  actual concurrent load per school regularly exceeds 3 simultaneous connections, requests will
  now queue and, past 5s, fail with a timeout error instead of eventually succeeding — this is
  the tradeoff HARDENING_PLAN §13 explicitly asks for (fail closed with a budget rather than
  silently allow unbounded connections), but it is a genuine capacity change worth watching after
  deploy, not a no-op.
- `GET /health/ready` gains a new possible `503` response (readiness timeout) it could not
  previously return (it would hang instead) — a monitoring/alerting consideration, not a schema
  change.
- No migration; no `apps/api-next` route/schema/HTTP-contract change beyond `/health/ready`'s new
  timeout behavior.

## 6. Compatibility/rollout plan

No feature flag. Recommend deploying with monitoring on connection-acquisition timeout errors and
`GET /health/ready` 503s immediately after rollout, specifically because §3's numbers are
placeholders — if acquisition timeouts appear under real traffic, raise `DB_SCHOOL_POOL_MAX`/
`DB_ACQUIRE_TIMEOUT_MS` via env var (no code change) rather than reverting the whole change. No
rollback concern beyond reverting `packages/db/src/index.ts` and the env additions (all new vars
have defaults, so removing them from the environment is also safe).

## 7. Acceptance criteria

- Every new env var has a default and is `z.coerce.number()`-validated; an invalid value (e.g.
  negative) fails startup validation rather than being silently coerced to `NaN`.
- A pool `'error'` event (simulate by emitting one directly on a test pool double, or by forcing
  a connection drop in an integration test once H1 lands) does not crash the process — it's
  caught and logged.
- `shutdownPools()` awaits a pool that was evicted from the cache immediately before shutdown was
  called (unit test: populate the cache past `DB_SCHOOL_POOL_CACHE_MAX`, trigger an eviction,
  immediately call `shutdownPools()`, assert it resolves only after the evicted pool's `.end()`
  resolves — mockable without a real Postgres).
- `GET /health/ready` returns `503` within `DB_READY_TIMEOUT_MS` (plus test tolerance) when the
  database check hangs past the deadline, verified with a stubbed `db.execute` that never
  resolves.
- `getPoolStats()` returns the real `totalCount`/`idleCount`/`waitingCount` from the underlying
  pools and the real cached-school count.
- Real-load acceptance (HARDENING_PLAN §13.3's "test at the approved maximum active-school
  count") is deferred to whenever the H1 harness lands and whenever real ops numbers replace
  this note's placeholders — recorded here, not silently dropped.
