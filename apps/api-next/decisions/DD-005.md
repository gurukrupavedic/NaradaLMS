# DD-005: Fix exam-list cross-product authorization

**Status:** proposed

## 1. Current behavior

Per PARITY_PLAN.md §11.1/§11.2, the current (implied old-backend-equivalent) approach to
"which exams can this educator see" independently builds a set of visible students and a
set of visible chapters and takes their cross-product. For an educator who manages
multiple batches, this can over-authorize: it can expose an exam pairing a student from
batch A with a chapter only taught in batch B, even though the educator never shares a
qualifying batch with that specific (student, chapter) pair.

## 2. Problem/opportunity

This is an authorization correctness bug (over-exposure), not a stylistic difference —
an educator could see exams they should not have visibility into. It's flagged as a
"proposed" decision rather than an auto-fix only because the parity plan's own rule is
that no behavior change proceeds without approval, even when the current behavior looks
like a bug.

## 3. Proposed behavior

Replace the cross-product with a correlated join/`EXISTS` query per PARITY_PLAN.md §11.1:
an exam is visible to an educator only if the educator is enrolled (instructor/TA) in a
**single batch** that simultaneously (a) has `batch.trackId === chapter.trackId` and (b)
contains the exam's `studentId` with role `student`.

## 4. Alternatives

- **Baseline:** reproduce the cross-product behavior exactly, including its
  over-authorization, to stay bit-for-bit compatible with today's (possibly buggy)
  behavior.
- **Proposed:** correlated qualifying-batch query (current draft direction, shared with
  DD-003/DD-004).

## 5. Impact analysis

This is a security-relevant tightening: some educators may lose visibility into exams
they could previously see (correctly, since that visibility was an authorization bug).
Confirm with the product owner whether any current workflow relies on the broader
(incorrect) visibility before shipping — e.g. an educator who manages Track A batch and
Track B batch might currently rely on seeing all of both tracks' exams from one dashboard
view, even where the pairing doesn't correlate.

## 6. Compatibility/rollout plan

No data migration. This is a pure read-path fix. Consider shipping behind a short
manual-verification window (compare old vs new endpoint output for the actual current
educator population) rather than a runtime feature flag, since this is a security fix,
not a UX change.

## 7. Acceptance criteria

Test per PARITY_PLAN.md §11.2/§11.7: educator with two batches on two different tracks
sees only exams whose student+chapter both correlate to a shared qualifying batch; the
old cross-product-leak case is explicitly asserted absent.

## 8. Manual approval record

this list that's a live authorization bug rather than a design preference.
