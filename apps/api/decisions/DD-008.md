# DD-008: Add `PUT` to CORS methods for the schedule route

**Status:** approved

## 1. Current behavior

The draft's CORS method allowlist (`apps/api-next/src/server.ts`,
`CORS_METHODS = ['GET', 'HEAD', 'POST', 'PATCH', 'DELETE', 'OPTIONS']`) does not include
`PUT`. PARITY_PLAN.md §9.5 specifies `PUT /batches/:batchId/schedule` as the recurring
class-schedule replace-set endpoint, which needs `PUT` in the CORS allowlist for browser
clients to call it cross-origin.

## 2. Problem/opportunity

Without `PUT` in `CORS_METHODS`, a browser preflight for `PUT /batches/:batchId/schedule`
will fail even if the route itself is implemented correctly. This is required
infrastructure for §9.5's endpoint, not an independent design choice — but per §1.1 item
10 (CORS is part of the compatibility baseline / runtime behavior), any CORS method-list
change formally needs approval.

## 3. Proposed behavior

Add `'PUT'` to `CORS_METHODS` in `server.ts`.

## 4. Alternatives

- **Baseline:** don't add `PUT`; implement the schedule route as `POST` or `PATCH`
  instead of `PUT` to avoid touching the CORS allowlist. Diverges from PARITY_PLAN.md
  §9.5's chosen verb (`PUT`, chosen for idempotent replace-set semantics) without a clear
  win.
- **Proposed:** add `PUT` to the CORS list (current draft direction, required for §9.5).

## 5. Impact analysis

Purely additive to the CORS allowlist; no existing route uses `PUT` today, so no
existing behavior changes. Only relevant consumer is the web app's schedule-editing UI
once it exists.

## 6. Compatibility/rollout plan

Land together with the `PUT /batches/:batchId/schedule` route itself in Phase 2 — there's
no reason to add the CORS method ahead of or separate from the endpoint it enables.

## 7. Acceptance criteria

CORS preflight (`OPTIONS`) test for `PUT /batches/:batchId/schedule` returns
`Access-Control-Allow-Methods` including `PUT`; other existing routes' preflight behavior
is unchanged.
