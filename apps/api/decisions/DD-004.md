# DD-004: Add and retain `GET /exams/:examId`

**Status:** approved

## 1. Current behavior

`apps/api/src` has no exam detail endpoint — only `GET /exams` (list). The draft already
implements `GET /exams/:examId` (`apps/api-next/src/exams/route.ts`).

## 2. Problem/opportunity

This is a genuinely new endpoint, not a behavior change to an existing one, so the
"approval" question here is narrower: should the draft keep a route the old backend never
had at all, and if so, must its visibility rules be provably equivalent to the list
endpoint's (so a caller can't read via ID something they couldn't see via list)?

## 3. Proposed behavior

Keep `GET /exams/:examId` as a draft-only extension. Visibility must exactly mirror
`GET /exams` scope resolution (all / own / manageable-via-qualifying-batch) — see
PARITY_PLAN.md §11.3: "A record hidden in list must not become readable by guessing its
ID."

## 4. Alternatives

- **Do not add:** drop the endpoint; only `GET /exams` exists, matching old backend
  1:1. Simplest, but removes an endpoint the web app may already be calling from the
  draft during development.
- **Proposed:** keep it, gated on list/detail visibility equivalence tests (current
  draft direction).

## 5. Impact analysis

Purely additive if kept — no existing caller depends on its absence. Main risk is
divergence between list-scope logic and detail-scope logic over time (two places to keep
in sync as DD-005's correlated-visibility fix lands).

## 6. Compatibility/rollout plan

No rollout coordination — additive endpoint. Should land in the same Phase 5 slice as
DD-005 so both use one shared visibility resolver rather than two independent
implementations that could drift.

## 7. Acceptance criteria

Contract test asserting: for every (actor, exam) pair used in the list-visibility test
matrix, `GET /exams/:examId` returns 200 iff the same exam appears in that actor's
`GET /exams` page, and 404 otherwise.
