# DD-002: Keep the draft's exam transition/concurrency hardening

**Status:** approved

## 1. Current behavior

`apps/api/src`'s exam update/result endpoints are the compatibility baseline: whatever
transitions and concurrency guarantees they currently provide (see `src/services/exam.ts`,
`src/routes/exams.ts`).

The draft has since been restructured (H2: repository/service split; H7: constraint-error
wrapping) but the concurrency shape this note describes is unchanged. As of this note's
update, the real code is:

- `apps/api-next/src/exams/transitions.ts`: `allowedTransitions` state machine
  (`scheduled -> inProgress | cancelled`, `inProgress -> cancelled`, `completed`/`cancelled`
  are terminal), enforced by `assertValidTransition`, covered by `transitions.test.ts`.
- `apps/api-next/src/exams/service.ts::updateExam`: reads the exam once (`existing`), validates
  the transition if `status` is supplied, then calls
  `repository.updateGuarded(context.db, id, data, existing.status)`.
- `apps/api-next/src/exams/repository.ts::updateGuarded`: `UPDATE exam SET ... WHERE id = ?
  AND status = ?` (the `?` is the status `updateExam` read before the write) — a correct
  optimistic compare-and-set. If it matches zero rows, `updateExam` re-reads the exam and
  throws `conflict('exam status changed concurrently')` if it still exists, `notFound()`
  otherwise.
- `apps/api-next/src/exams/service.ts::recordExamResult`: reads the exam once (`existing`),
  checks `RECORDABLE_STATUSES.includes(existing.status)` (`'scheduled' | 'inProgress'`)
  **before** opening a transaction, then inside `context.db.transaction(tx => ...)`: inserts
  the evaluation, then calls `repository.complete(tx, id, evalRow.id, new Date())`.
- `apps/api-next/src/exams/repository.ts::complete`: `UPDATE exam SET evaluationId = ?,
  performedAt = ?, status = 'completed' WHERE id = ? AND evaluationId IS NULL`. **This guard
  does not reference `status` at all** — only `evaluationId IS NULL`.

**The gap, traced concretely:** exam starts `scheduled`.
1. Request A (`PATCH .../exams/:id` with `status: 'cancelled'`) reads `existing.status =
   'scheduled'`, calls `updateGuarded(id, {status:'cancelled'}, 'scheduled')`, commits. Exam is
   now `status='cancelled'`, `evaluationId` still `NULL`.
2. Request B (`POST .../exams/:id/results`), racing concurrently, reads `existing.status` at
   some point before or after step 1 and passes the `RECORDABLE_STATUSES` precheck (which only
   requires the status *it read* to be recordable — it does not re-check after A commits).
   B's transaction inserts an evaluation, then calls `complete(tx, id, evalRow.id, now)`. That
   UPDATE's `WHERE id = ? AND evaluationId IS NULL` **still matches** — A's cancellation never
   touched `evaluationId`. B's update succeeds: the exam becomes `status='completed'`,
   silently overwriting A's committed cancellation.

So: two simultaneous *results* are correctly race-safe today (both would hit `complete`'s
`evaluationId IS NULL` guard; only one wins, the loser rolls back and gets `conflict('a result
was already recorded for this exam')`) — `updateGuarded`'s own compare-and-set is also correct
in isolation. The gap is specifically **a result racing a cancellation**: the two guards
(`updateGuarded`'s status compare-and-set, `complete`'s `evaluationId IS NULL`) don't share a
single check, so a request that goes through `complete` never learns that the status changed
out from under it.

## 2. Problem/opportunity

This is exactly the kind of "internal pattern" §1.3 allows without approval **if** it
preserves every externally observable compatibility-baseline item — but PARITY_PLAN.md
§11.5–§11.6 treats it as a candidate improvement because it isn't yet verified that the
old backend's observable transition/concurrency behavior is identical.

**Now verified, by reading `apps/api/src/services/exam.ts` directly:** the old backend has
*no* concurrency protection at all, on either endpoint.

- `updateExam` (line 177): `UPDATE exam SET ... WHERE id = examId` — no status predicate. Any
  two concurrent updates both "succeed"; the request that commits last silently wins with no
  conflict signal, including a transition the state machine below would forbid (the old backend
  has no transition table either — any `status` value is accepted unconditionally).
- `recordExamResult` (line 191): `UPDATE exam SET evaluationId = ..., status = 'completed' WHERE
  id = examRecord.id` — no `evaluationId IS NULL` guard, no status guard. Two concurrent result
  submissions both insert an evaluation and both "complete" the exam; the exam ends up pointing
  at whichever evaluation's UPDATE committed last, and the other evaluation becomes a
  permanent orphan row with no exam referencing it. A result racing a cancellation has the exact
  same silent-overwrite problem this note describes for the draft, except the draft's gap is one
  specific race order the old backend doesn't protect against under **any** order.

So there is no compatibility-baseline behavior to preserve here beyond the single-request
success path (create/read/list), which this proposal doesn't touch. This isn't a case of
"the draft might be accidentally stricter than production" — production has strictly weaker
guarantees on every axis. Approving DD-002 cannot regress a real production concurrency
guarantee, because none currently exists.

## 3. Proposed behavior

Retain the draft's state machine and `updateGuarded`'s optimistic update guard exactly as they
are — neither has the gap. Change only `repository.complete` and its one caller,
`service.ts::recordExamResult`:

**`repository.complete`** gains an `expectedStatus` parameter and adds it to the `WHERE`:

```ts
export async function complete(
  db: SchoolDb,
  id: string,
  evaluationId: string,
  performedAt: Date,
  expectedStatus: Exam['status'],
): Promise<Exam | undefined> {
  const rows = await db
    .update(exam)
    .set({ evaluationId, performedAt, status: 'completed' })
    .where(and(eq(exam.id, id), isNull(exam.evaluationId), eq(exam.status, expectedStatus)))
    .returning()
  return rows.at(0)
}
```

**`service.ts::recordExamResult`** passes `existing.status` (the exact status it already read
before opening the transaction — not re-read) as `expectedStatus`, and, on a lost race,
distinguishes *why* it lost instead of assuming it was always a double-result:

```ts
const row = await repository.complete(tx, id, evalRow.id, new Date(), existing.status)
if (!row) {
  const current = await repository.findById(tx, id)
  if (!current) throw notFound()
  if (current.evaluationId) throw conflict('a result was already recorded for this exam')
  throw conflict('exam status changed concurrently')
}
return row
```

Both throws happen inside the transaction callback, so the evaluation insert still rolls back
either way (per the transaction doc comment already on this function — unchanged mechanism, H7
confirmed a substituted throw here still triggers `ROLLBACK`). The distinguishing read
(`current.evaluationId` set vs. not) reuses the exact same pattern `updateExam` already uses to
tell "status changed" apart from "gone" — this proposal makes `recordExamResult` follow that
same established shape rather than inventing a new one.

This closes exactly the gap in §1: a committed cancellation changes `exam.status` away from
`existing.status`, so `complete`'s guard now fails, the evaluation insert rolls back, and the
racing result gets `409 'exam status changed concurrently'` instead of silently completing.

## 4. Alternatives

- **Baseline:** reimplement `apps/api/src/services/exam.ts` exactly, including its lack of any
  concurrency guard. Rejected: this is strictly worse than what's already committed to
  `apps/api-next` (H2/H7), including introducing the double-result orphan-evaluation bug that
  the draft's `evaluationId IS NULL` guard already prevents.
- **Existing draft guard (no change):** keep `complete`'s `evaluationId IS NULL`-only guard,
  accept that a committed cancellation can be silently overwritten by a later result. Rejected:
  this is the bug DD-002 exists to close; leaving it means the codebase already contains code
  (`complete`, `recordExamResult`) whose doc comment claims stronger guarantees than it provides.
- **Proposed:** add `expectedStatus` to `complete`'s guard (§3). Minimal, reuses the exact
  pattern `updateExam` already established for distinguishing a lost race from a missing row.
- **Row locking (`SELECT ... FOR UPDATE`) instead of compare-and-set:** lock the exam row at the
  start of the transaction instead of comparing a pre-read status. Would also close the gap, but
  changes the transaction's isolation behavior for every result-recording request (not just the
  losing side of a real race) and is a larger deviation from the existing optimistic-concurrency
  style already used by `updateGuarded`. Rejected in favor of consistency with the pattern
  already in this module.

## 5. Impact analysis

Affects only `POST /exams/:examId/results`'s one race window (concurrent cancellation vs.
result recording); `PATCH /exams/:examId` (`updateGuarded`) and the transition state machine
are unchanged by this proposal — they're already correct (§1) and not being modified. No
migration. No client-visible change on any single-request path; the only observable difference
is that the specific race in §1 now returns `409 'exam status changed concurrently'` instead of
silently completing the exam — since that race currently has no defined contract (and the old
backend doesn't protect against it at all, per §2), there's no existing client behavior to
preserve or break here.

## 6. Compatibility/rollout plan

No dependency on the exam ACL work. `exams/route.ts` currently gates create/update/results as
school-admin-only (see its own `TODO`, pending the instructor/TA batch-resolution work in
PARITY_PLAN.md §11.1/DD-003–DD-005) — this proposal doesn't touch authorization, only the
result-recording transaction's guard, so it lands independently of when the ACL work ships. No
flag needed; this is server-side only, no schema/migration change.

## 7. Acceptance criteria

`transitions.test.ts`'s full transition table (already present, unaffected by this change)
stays green. New coverage needed, concretely:

- **Unit/service-level (mock-based, matching the pattern already established in
  `exams/service.test.ts` for H7 — no real DB required):** `recordExamResult` calls
  `repository.complete` with `existing.status` as the `expectedStatus` argument (assert the
  mock was called with that exact value); when `complete` resolves `undefined` and a
  follow-up `repository.findById` shows `evaluationId` set, throws `conflict('a result was
  already recorded for this exam')`; when `complete` resolves `undefined` and the follow-up
  read shows `evaluationId` still `null` (status changed instead), throws `conflict('exam
  status changed concurrently')`; when the follow-up read finds no row, throws `notFound()`.
- **Real-concurrency proof (needs a real Postgres and the barrier mechanism — i.e. the H1
  harness once it lands, currently stashed):**
  - cancellation commits first, then a racing result attempt: exam remains `cancelled`,
    evaluation count stays zero, the result request gets `409 'exam status changed
    concurrently'`.
  - a racing result commits first, then a cancellation attempt: exam is `completed` with one
    evaluation; the cancellation gets `409` via `updateGuarded`'s existing (already correct)
    guard.
  - two simultaneous result attempts: exactly one commits, one evaluation exists, the loser
    gets `409 'a result was already recorded for this exam'` (this path is already correct
    today and must remain so — a regression test, not new behavior).
  - no orphan evaluation row survives any losing transaction, in any of the above.

This DD's real-DB acceptance criteria are explicitly deferred to whenever H1 lands, matching
how DD-001 §7 handled the same dependency — approval of this note does not require the harness
to exist yet, only that the unit-level criteria above are implemented and passing.

The wider exam acceptance matrix remains in `PARITY_PLAN.md` §11.7.
