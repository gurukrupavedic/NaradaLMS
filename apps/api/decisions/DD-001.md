# DD-001: Use `translateDbError` as a final race-safe mapping for unique/FK failures

**Status:** approved

## 1. Current behavior

`apps/api/src` (old backend) has no centralized database-error translation layer (no
`dbError.ts` equivalent; grep for `unique_violation`/`23505`/`23503`/`PostgresError` in
`apps/api/src` returns nothing). Endpoints instead do a check-then-write precheck — e.g.
`src/routes/batches.ts` calls `findBatchById` before update/delete to decide 404 vs proceed,
but does not catch a unique/foreign-key violation that a concurrent request could still
trigger between the check and the write. In that race, the current backend most likely
surfaces an unhandled 500 rather than a domain 409/422.

`apps/api-next` (draft) already has a translator (`src/utils/dbError.ts`), wired as the
**only** database-error handling: `server.ts`'s error middleware calls
`translateDbError(error)` as a fallback whenever a thrown value isn't already an `AppError`.
No domain service currently catches a constraint violation itself — every DB-error response
in the draft today goes through this one generic mapping:

```ts
23505 (unique_violation)      → 409 'a resource with these values already exists'
23503 (foreign_key_violation) → 422 'referenced resource does not exist'
```

This is exactly the coarse mapping this note's "Problem" section describes, and it is
**already observably wrong** for one real, reachable-today path: `DELETE
/profiles/:profileId` (`profiles/service.ts` → `repository.deleteOwned`) issues a raw
`DELETE FROM profile WHERE id = ? AND userId = ?`. If that profile is referenced by
`evaluation.evaluatorId` (`ON DELETE RESTRICT`) — which happens routinely, since
`exams/service.ts`'s `recordExamResult` inserts an evaluation with `evaluatorId` set to the
acting profile — the delete raises `23503`, and today's translator reports "referenced
resource does not exist" even though the true problem is the opposite: this profile **is**
referenced and can't be removed while it is. This is not a hypothetical race; it's the
current, deterministic response to an ordinary sequence (record a result, then try to delete
that evaluator's profile).

## 2. Problem/opportunity

Check-then-write has a TOCTOU gap under concurrent requests (e.g. two clients creating a
batch with the same `code` at once, or inserting an evaluation referencing a
just-deleted chapter). `apps/api-next/src/utils/dbError.ts` already exists and is unit
tested (`dbError.test.ts`); using database constraints as the final race-safe guard would make
these failures return a controlled domain response instead of leaking a raw 500.

The current translator is too coarse to be the complete solution: SQLSTATE `23503` can mean
either that an inserted parent does not exist or that a delete/update is blocked by an existing
child. Mapping both cases to `referenced resource does not exist` is incorrect. For example, an
evaluator-profile delete blocked by `evaluation.evaluatorId` is a resource-in-use conflict, not
a missing reference.

## 3. Proposed behavior

Use two translation layers:

1. A domain service maps known constraint names plus operation context to the same specific
   `AppError` the friendly precheck path would have produced.
2. `translateDbError` remains a final safety net for recognized integrity failures, but returns
   only a truthful generic response when domain meaning is unavailable. It must not claim that a
   referenced resource is missing merely because the SQLSTATE is `23503`.

This retains database constraints as the race-safe authority while allowing create-side missing
references, delete-side resource-in-use conflicts, and unique violations to have different
semantics.

### 3.1 Concrete constraint-to-response mapping

Every constraint below is real (grep-verified against the generated migrations in
`packages/db/drizzle/{public,school}/0000_*.sql` and `0001_supreme_nocturne.sql`), and every
"Reachable via" operation exists in `apps/api-next/src` today. This table is what an
approver is actually approving — the domain service named in "Reachable via" is where the
constraint-name check is added (layer 1); `translateDbError` (layer 2) keeps its current
generic behavior for anything not in this table.

| Constraint (real name)                       | Table.column(s)                         | Reachable via                                             | Meaning                             | Current response                        | Proposed response                                          |
| ---------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------- | ------------------------------------ | ------------------------------------------ | -------------------------------------------------------------- |
| `batch_trackId_track_id_fk`                    | `batch.trackId → track.id`               | `batches/service.ts::createBatch`                          | Insert references a missing track    | 422 generic "referenced resource does not exist" (accidentally correct-shaped, wrong wording) | 422 `unknown or invalid track`                                  |
| `batch_code_unique`                            | `batch.code`                             | `batches/service.ts::createBatch`, `updateBatch`            | Duplicate batch code                 | 409 generic (accidentally correct)         | 409 `a batch with this code already exists`                    |
| `exam_studentId_profile_id_fk` / `exam_chapterId_chapter_id_fk` | `exam.studentId`/`exam.chapterId → profile.id`/`chapter.id` | `exams/service.ts::createExam` (race window between `assertValidExamAssignment`'s precheck and the insert) | Student or chapter deleted concurrently with exam creation | 422 generic (accidentally correct-shaped) | 422 `student or chapter no longer exists` |
| `evaluation_studentId_profile_id_fk` / `evaluation_chapterId_chapter_id_fk` / `evaluation_evaluatorId_profile_id_fk` | `evaluation.*Id → profile.id`/`chapter.id` | `exams/service.ts::recordExamResult` (inside the transaction, `repository.insertEvaluation`) | Referenced student/chapter/evaluator deleted concurrently with result recording | 422 generic (accidentally correct-shaped) | 422 `student, chapter, or evaluator no longer exists` |
| `evaluation_evaluatorId_profile_id_fk` (RESTRICT on delete) | `profile` blocked by `evaluation.evaluatorId` | `profiles/service.ts::deleteById` → `repository.deleteOwned` | Profile still referenced as an evaluator | **422 "referenced resource does not exist" — actively wrong** | **409 `profile is still referenced by an evaluation and cannot be deleted`** |
| `member_organizationId_userId_uidx` (added in H4) | `member.(organizationId, userId)`        | Not yet reachable from `apps/api-next` (no membership-write route exists today); BetterAuth's own organization-invitation-accept path writes `member` rows | Duplicate membership          | n/a today (draft has no write path)        | 409 `already a member of this organization` (when a write path exists) |
| Anything else (unrecognized constraint name)   | —                                         | any                                                          | Meaning unavailable to the operation | current generic mapping                   | unchanged: safe generic 409/422 per SQLSTATE, exact prose TBD by implementer |

Row 5 (profile delete blocked by evaluator reference) is the one existing, concretely wrong
behavior this decision fixes. Rows 1–4 already happen to return roughly the right status code
today because the generic FK mapping (422 "referenced resource does not exist") coincides with
the create-side meaning; the change there is precision of wording and moving the check to
where the domain context is known, not a status-code change. Row 6 documents that H4 (already
landed) makes a duplicate-membership constraint exist, but no `apps/api-next` write path can hit
it yet — include it in the mapping now so whichever future PR adds a membership-write route
doesn't have to revisit this decision.

## 4. Alternatives

- **Baseline (no change):** keep relying solely on check-then-write; concurrent races
  produce a 500. Simpler, but reintroduces a known race class the draft already has
  tooling to close.
- **SQLSTATE-only translation:** keep the current draft's global 409-for-unique and 422-for-FK
  mapping. Simple, but produces false messages and sometimes the wrong status for delete-side
  violations.
- **Proposed:** constraint/operation-aware domain translation plus a conservative global safety
  net.
- **Precheck + row-level lock:** use `SELECT ... FOR UPDATE` or a serializable
  transaction instead of relying on constraint-violation translation. More invasive,
  changes transaction shape for every affected write, not clearly justified here.

## 5. Impact analysis

- Affects the operations in §3.1's table today: `batches::createBatch`/`updateBatch`,
  `exams::createExam`/`recordExamResult`, `profiles::deleteById`. Enrollment/evaluation-write
  and school-slug endpoints aren't implemented in `apps/api-next` yet (per `PARITY_PLAN.md`);
  their constraint mappings get added when those domains land, following this same pattern.
- No schema/migration impact — purely error-handling.
- **One real status-code change, not just a race-condition improvement:** `DELETE
  /profiles/:profileId` on a profile still referenced as an evaluator changes from 422 to 409.
  This is a client-visible contract change on a currently-reachable path (not a rare race), so
  any web client handling of that specific 422 needs to be checked before/alongside rollout.
- All other rows in §3.1 keep their current status code; only response wording changes.
- Observability: fewer unhandled 500s in logs for the create-side race window; should reduce
  noise, not increase it.

## 6. Compatibility/rollout plan

No rollout coordination needed for §3.1's rows 1–4 and 6 — those only change behavior on a
race window or an unreachable path that currently has no defined contract. **Row 5 (profile
delete blocked by an evaluator reference) does need a check before rollout**: confirm
`apps/web`'s profile-deletion UI doesn't special-case the current 422 in a way that would
mishandle a 409 instead (a quick grep of its error-handling for that call didn't find a
specific 422 branch, but this should be verified by whoever implements the change, not
assumed from this note). No feature flag needed either way — this is a same-release change,
not a staged migration. No rollback concern beyond reverting the middleware/service wiring.

## 7. Acceptance criteria

- **The one behavior-changing case, tested explicitly:** deleting a profile that is referenced
  by `evaluation.evaluatorId` returns 409 `profile is still referenced by an evaluation and
  cannot be deleted`, not 422. A profile with no evaluator references still deletes normally.
- `POST /batches` with a nonexistent `trackId` returns 422 with a message naming the track,
  not the generic "referenced resource does not exist".
- `POST /batches` / `PATCH /batches/:batchId` with a duplicate `code` returns 409 with a message
  naming the duplicate code conflict.
- A test that fires two concurrent `POST /batches` with the same `code` and asserts exactly one
  2xx and one clean 409 (no 500, no unhandled rejection) — this is the race §2 exists to close,
  using the H1 harness's barrier helper once it's available for this domain.
- `POST /exams` and `POST /exams/:examId/results` each get a test where the referenced
  student/chapter/evaluator is deleted between the service's precheck and the insert (or, until
  the H1 barrier supports this interleave for exams, a direct repository-level test that deletes
  the row before calling `insert`/`insertEvaluation`) — asserts the domain 422, not 500.
- `dbError.test.ts`'s existing generic-fallback tests (unique/FK/unrecognized/non-pg-error)
  keep passing unchanged — layer 2 (`translateDbError`) is not being narrowed, only
  supplemented by layer 1.
- An unknown integrity constraint (not in §3.1's table) still returns `translateDbError`'s
  current safe generic response, with the constraint name available in logs but never in the
  API response body.
